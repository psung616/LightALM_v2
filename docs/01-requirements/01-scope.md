## 1. 프로젝트 목적 및 핵심 스코프

### 1.1 목적
중소 규모 개발팀이 무거운 ALM 툴 없이도 다음 세 가지 핵심 기능만으로 소프트웨어 개발 생명주기를 관리할 수 있게 한다.

1. **요구사항 관리** — 요구사항 등록/분류/상태 추적, 상위-하위 요구사항 계층 구조
2. **이슈 트래킹** — 버그/작업/스토리 단위 이슈 생성, 담당자 지정, 상태 전이
3. **추적성 관리(Traceability)** — 요구사항 ↔ 이슈 간 연결, 커밋/PR/빌드까지 연결하여 "요구사항이 실제로 어떤 코드/빌드로 구현·검증되었는지" 추적

- **프로젝트별 열거형(PRIORITY) 확장** — `PROJECT_ADMIN`이 PRIORITY 값 목록을 프로젝트 단위로 추가. 요구사항/이슈/테스트케이스 상태(Status) 값 자체의 확장은 이번 범위에서 제외(별도 ADR 필요, ADR-012 §C.1 참고). ADR-012 §C 참고

### 1.3 명시적 비스코프 (Light 버전에서 제외)
아래 항목은 이번 버전에서 **구현하지 않는다.** Claude는 이 항목들에 대한 기능을 임의로 추가하지 않는다.
- 스프린트/애자일 보드(백로그, 스프린트 계획, 번다운 차트)
- **범용** 워크플로우 엔진(조건 분기, 전이 시 자동 액션, 다단계 승인자 체인 등을 포함하는 엔진)은 제외. 다음 두 가지만 좁은 예외로 허용한다: (1) §1.2의 승인 워크플로우 — `요구사항 DRAFT→APPROVED` 전이 1건만 게이팅. (2) §1.2 v4 확장의 프로젝트별 워크플로우 전이 규칙(ADR-012 §D) — "상태 A→B 허용 여부 + 최소 역할"만 표현하는 화이트리스트 매트릭스. 두 예외 모두 적용되지 않는 한 모든 상태 전이는 자유 전이다
- **완전 자유 스키마** 커스텀 필드(필드 간 조건부 로직, 수식/계산 필드, 프로젝트 간 필드 공유 등)는 제외. 단 §1.2 v4 확장의 프로젝트별 커스텀 필드(ADR-012 §A — 정해진 데이터 타입 목록 안에서 요구사항/이슈/테스트케이스에 추가 속성 몇 개를 붙이는 EAV 패턴)는 허용한다
- 알림/이메일 발송, 실시간 웹소켓 알림
- 파일 첨부(첨부파일 업로드 기능은 제외, 텍스트/링크로만 참조)
- 다국어(i18n) — 한국어 단일 언어로 구현
- SSO/OAuth 로그인 — 자체 폼 로그인만 지원
- 세밀한 권한 매트릭스(프로젝트 역할은 3단계: PROJECT_ADMIN / MEMBER / VIEWER로 단순화 — 화면 표시명은 §1.4 참고)

### 1.4 사용자 역할
> 역할 **값**(DB/코드/API)은 그대로 두고 **화면 표시명**만 아래처럼 쓴다(ADR-015 D1, 매핑은 `frontend/src/auth/roleDisplayNames.ts` 한 곳). 시스템 역할 `USER`("User")와 프로젝트 역할 `VIEWER`("Project User")는 다른 개념이다.

- **시스템 역할(User.role)**: `ADMIN` = **System Admin**(시스템 전체 관리자 — 계정 생성/수정/비활성화, System Admin 부여·해제, 시스템 테마, **프로젝트 생성**. 모든 프로젝트에서 Project Admin 이상으로 취급), `USER` = **User**(일반 사용자 — 프로젝트 권한은 각 프로젝트의 멤버 역할로 결정)
- **프로젝트 역할(ProjectMember.role)**: `PROJECT_ADMIN` = **Project Admin**(프로젝트의 모든 설정, 멤버/역할 부여, 삭제·릴리스·베이스라인·승인 결정), `MEMBER` = **Project Assignable**(읽기 + 쓰기 — 요구사항/이슈/테스트케이스 생성·수정·상태 변경 등. 설정 변경 불가), `VIEWER` = **Project User**(읽기 전용. 유일한 예외: 본인이 참여자로 지정된 리뷰 사이클의 결정 기록, ADR-015 P1)
- **계정 생성과 프로젝트 생성은 System Admin만** 한다(ADR-015 D2·D6). 공개 회원가입 없음. 프로젝트를 만든 System Admin은 그 프로젝트의 `PROJECT_ADMIN` 멤버로 자동 등록되고, 실제 담당 Project Admin은 생성 후 멤버 탭에서 지정한다.
- **활성 System Admin은 항상 1명 이상** 유지된다(ADR-015 D3). 유일한 활성 `ADMIN`을 해제하거나 비활성화하는 요청은 `400 LAST_ACTIVE_ADMIN`으로 거부된다(애플리케이션 레벨 강제).
