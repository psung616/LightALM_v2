# ADR-013: 프로젝트 사이드바 — PRD/SRS/Defect/TestCase 작업 항목 유형별 트리 패널

## 맥락 (Context)

제품 오너가 "프로젝트 안에서 좌측 패널(사이드바)을 통해, 그 프로젝트 권한을 가진 사용자가 프로젝트 안에서 생성된 **PRD / SRS / Defect(결함) / TestCase**를 유형별로 확인할 수 있게" 해달라고 요청했다. 재질의로 다음 세 가지가 확정됐다(추측하지 않고 그대로 반영).

1. **PRD/SRS/Defect/TestCase의 정체**: 업계 상용 ALM 툴(예: Polarion류)에서 쓰는 업무 프로세스 개념으로, 이 네 가지는 서로 동급의 "작업 항목 유형"이다. 서로 자유롭게 추적성 연결이 가능해야 하고, 고정된 상하 계층은 강제되지 않지만 **사용자가 판단해서 임의로 상하 관계를 만들 수 있어야 한다.**
2. **패널 범위**: 현재 진입한 프로젝트 **안에서만** 유형별 트리를 보여준다. 여러 프로젝트를 한 화면에 나열하는 전역 탐색기가 아니다.
3. **표시 대상**: 그 프로젝트에 속한 데이터 전체(프로젝트 멤버 전원이 만든 것)를 보여준다 — "내가 만든 것"으로 필터링하지 않는다.

### 기존 코드/데이터 조사 결과 (오케스트레이터 사전 확인, 설계에 그대로 활용)
- **`traceability_links`(03-data-model.md §3.6)**: 이미 `source_type`/`target_type`을 조합해 연결하는 **범용 연결 테이블**이다. `target_type`은 `REQUIREMENT`/`ISSUE`/`TEST_CASE`(v3에서 `RISK` 추가 예정)를 허용하지만, **`source_type`은 현재 `REQUIREMENT`/`ISSUE`만 허용**한다(`V1__init.sql`의 `chk_traceability_links_source_type`). 즉 "요구사항↔이슈", "요구사항↔테스트케이스", "이슈↔테스트케이스"는 되지만 **테스트케이스를 출발점(source)으로 하는 링크는 현재 막혀 있다** — 이 ADR에서 반드시 짚어야 하는 기존 비대칭이다(§1.3 참고).
- **`issues.type`**: 이미 `CHECK (type IN ('BUG','TASK','STORY','IMPROVEMENT'))`로 `BUG`가 존재한다. "Defect"는 기존 `Issue` 엔티티의 `type='BUG'` 필터 뷰로 표현 가능하다.
- **`requirements.parent_requirement_id`**: 이미 nullable self-FK로 선택적 상하 계층을 지원한다(§3.4). "위아래 구분은 없지만 사용자 판단으로 구분 가능"이라는 요구사항과 정확히 일치하는 기존 메커니즘이다.
- **`PRD`에 해당하는 기존 엔티티는 없다.** `requirements`에 이미 `type`(`FUNCTIONAL`/`NON_FUNCTIONAL`/`BUSINESS` — 요구사항의 "성격" 분류) 컬럼이 있지만, 이것은 PRD/SRS가 구분하려는 "문서 레벨"과는 다른 축이다. **TestCase**는 이미 독립 엔티티로 존재한다.

### 저작권/용어 검토
"PRD"(Product Requirements Document), "SRS"(Software Requirements Specification), "Defect", "Test Case"는 소프트웨어 공학에서 범용적으로 쓰이는 표준 용어이며 특정 제품의 상표화된 기능명이 아니다(`02-competitive-reference.md` 원칙 3의 "상표화된 기능명"에 해당하지 않음). 따라서 이 용어들을 그대로 쓰는 것은 저작권/상표 리스크가 없다고 판단한다. 단, 화면 UI(레이아웃/색상/아이콘)는 특정 제품을 참고하지 않고 이 프로젝트의 디자인 시스템을 그대로 쓴다(기존 원칙 유지).

### `01-scope.md` 반영 필요 여부 — 판단
이 기능은 `01-scope.md` §1.2에 이미 있는 "요구사항 CRUD + 계층 구조", "이슈 CRUD", "테스트케이스 관리", "요구사항 ↔ 이슈 추적성 링크"의 **자연스러운 조회 UI 확장**이며, §1.3의 어떤 비스코프 항목과도 정면 충돌하지 않는다(ADR-012처럼 비스코프 해제가 필요한 사안이 아니다). 신규로 추가되는 것은 (a) `requirements`에 컬럼 하나, (b) 기존 `traceability_links` CHECK 제약의 비대칭 보강, (c) 순수 조회 성격의 사이드바 UI뿐이다. **따라서 이 ADR은 스코프 확장 승인이 필요하지 않다고 판단한다.** 다만 추적 가능성을 위해 `01-scope.md` §1.2의 관련 bullet에 한 줄 참조를 추가하는 것을 권장하되, 이번 ADR 범위에는 포함하지 않는다(오케스트레이터 판단에 맡김).

## 결정 (Decision)

### 0. 옵션 비교 및 추천

| 기준 | 옵션 1: 최소 변경(기존 인프라 재사용) | 옵션 2: 범용 WorkItem 모델 |
|---|---|---|
| 변경 범위 | `requirements`에 컬럼 1개 추가, `traceability_links` CHECK 1곳 보강, 신규 API 쿼리 파라미터 2개, 신규 프론트 컴포넌트 1개 | `Requirement`/`Issue`/`TestCase` 16개 엔티티 중 다수를 `WorkItem` 상위 개념으로 재설계 |
| 영향받는 기존 코드 | 거의 없음(추가적이고 하위 호환) | Phase 0~15 전체(엔티티/리포지토리/서비스/컨트롤러/프론트 전부) |
| 기존 인프라 재사용도 | 100% (`traceability_links`, `parent_requirement_id`, `issues.type`, `test_cases` 그대로) | 0% (전부 재설계) |
| Light 철학 부합 | 부합(불필요한 복잡도 없음, `docs/CLAUDE.md` 과설계 방지 원칙) | 위반 위험 큼 — 지금 요구사항(사이드바 그룹핑 조회)에 비해 과도 |
| 리스크 | 낮음 | 매우 높음(운영 중인 서비스의 데이터 모델 근본 변경) |

**옵션 1을 채택한다.** 지금 요구되는 것은 "4개 유형으로 묶어서 사이드바에 보여주고 서로 자유롭게 연결 가능하게 한다"는 **조회·연결 편의 기능**이지, 엔티티 구조 자체를 통합해야 할 필요는 없다. 이미 존재하는 범용 연결 테이블(`traceability_links`)과 선택적 계층(`parent_requirement_id`)이 "서로 자유롭게 연결되고, 상하 구분은 사용자 판단"이라는 요구사항을 그대로 만족시킨다. 옵션 2는 이번 요구사항 대비 변경 반경이 과도하고, 이 프로젝트가 ADR-008/ADR-012에서 반복적으로 지켜온 "최소 스코프로 개념만 들여온다"는 원칙과도 맞지 않는다.

### 1. 데이터 모델 변경

#### 1.1 `requirements.requirement_level` (신규 컬럼)
PRD와 SRS를 구분하기 위해 `requirements` 테이블에 컬럼 하나를 추가한다.

| 컬럼 | 타입 | 제약 |
|---|---|---|
| requirement_level | VARCHAR(10) | NOT NULL, CHECK IN ('PRD','SRS'), DEFAULT 'SRS' |

- 기존 `requirements.type`(`FUNCTIONAL`/`NON_FUNCTIONAL`/`BUSINESS`, §3.4)과는 **다른 축**이다. `type`은 요구사항의 "성격"을, `requirement_level`은 "문서 레벨(제품 수준 vs 소프트웨어 수준)"을 나타낸다. 두 축을 하나의 컬럼으로 합치지 않는다 — 혼동을 줄이기 위해 요구사항 생성/수정 폼에서 두 필드를 라벨/도움말 문구로 명확히 구분해서 보여준다(§3 UI 참고).
- 기존 데이터는 모두 `'SRS'`로 백필한다(하위 호환 — `requirement_level` 필터를 쓰지 않는 기존 조회는 전혀 영향받지 않는다).
- PRD/SRS 사이의 상하 관계는 **강제하지 않는다.** 즉 `parent_requirement_id`가 PRD를 가리키든 SRS를 가리키든, 혹은 `requirement_level`과 무관하게 어떤 조합이든 DB 레벨에서 막지 않는다 — "위아래 구분은 없지만 사용자 판단으로 구분 가능"이라는 제품 오너의 명시적 요청을 그대로 반영한 결정이다.

마이그레이션(참고용, 실제 파일은 생성하지 않음, 번호는 구현 시점 디렉터리 상태 기준으로 확정):
```sql
ALTER TABLE requirements ADD COLUMN IF NOT EXISTS requirement_level VARCHAR(10) NOT NULL DEFAULT 'SRS';
ALTER TABLE requirements ADD CONSTRAINT chk_requirements_requirement_level CHECK (requirement_level IN ('PRD','SRS'));
```

#### 1.2 Defect — 신규 엔티티/컬럼 없음
"Defect"는 기존 `issues` 테이블의 `type='BUG'` 필터 뷰로 표현한다. 스키마 변경이 전혀 없다.

#### 1.3 TestCase — 변경 없음
기존 `test_cases` 테이블을 그대로 쓴다.

#### 1.4 `traceability_links.source_type` CHECK 보강 — 대칭성 확보
제품 오너의 "이것들은 서로 추적성 연결이 되어야 한다"는 요구를 **완전히** 만족시키려면, 현재 `TEST_CASE`가 `target_type`에는 있지만 `source_type`에는 없는 비대칭을 해소해야 한다(위 "기존 조사 결과" 참고). 그렇지 않으면 "테스트케이스가 이 결함을 발견했다"처럼 테스트케이스를 출발점으로 하는 링크를 만들 수 없다.

마이그레이션(참고용):
```sql
ALTER TABLE traceability_links DROP CONSTRAINT IF EXISTS chk_traceability_links_source_type;
ALTER TABLE traceability_links ADD CONSTRAINT chk_traceability_links_source_type
    CHECK (source_type IN ('REQUIREMENT','ISSUE','TEST_CASE'));
```
> 기존 운영 데이터는 전부 `source_type IN ('REQUIREMENT','ISSUE')`이므로 이 제약 완화는 항상 하위 호환이다(기존 행이 새 제약을 위반할 가능성 없음). `RISK`(v3, ADR-008/§3.22)는 이 ADR의 범위가 아니므로 함께 추가하지 않는다 — 필요해지면 v3 Phase 착수 시 별도로 처리한다.
> **새 `TargetType` 값을 추가하는 것이 아니다.** 기존 세 값(`REQUIREMENT`/`ISSUE`/`TEST_CASE`)의 `source_type`/`target_type` 허용 범위를 대칭으로 맞추는 것뿐이므로, `PolymorphicTargetValidator`(ADR-010)와 `GLOSSARY.md` §3의 `TargetType` enum 값 자체는 변경되지 않는다.

### 2. API 변경 (전부 additive, 기존 계약 변경 없음)

| 변경 대상 | 내용 |
|---|---|
| `GET /api/projects/{projectId}/requirements` | 선택적 쿼리 파라미터 2개 추가: `requirementLevel`(`PRD`\|`SRS`), `rootOnly`(boolean — `parent_requirement_id IS NULL`인 것만). 둘 다 생략 시 기존과 동일하게 동작(하위 호환) |
| `POST /api/projects/{projectId}/requirements` | 요청 바디에 `requirementLevel` 선택 필드 추가(생략 시 서버가 `'SRS'`로 저장) |
| `PUT /api/projects/{projectId}/requirements/{reqId}` | 수정 가능 필드에 `requirementLevel` 추가 |
| `GET /api/projects/{projectId}/requirements/{reqId}/children` | **변경 없음** — 사이드바 트리의 자식 노드 지연 로딩에 그대로 재사용(기존 §4.5) |
| `GET /api/projects/{projectId}/issues` | **변경 없음** — 기존 `type` 필터(`type=BUG`)로 Defect 뷰를 구성 |
| `GET /api/projects/{projectId}/test-cases` | **변경 없음** |
| `traceability-links` 생성/조회 API(§4.7) | API 바디/응답 포맷 변경 없음 — DB CHECK만 넓어지므로 이제 `source_type='TEST_CASE'` 요청이 추가로 통과할 뿐 |

새 컨트롤러/신규 엔드포인트가 필요하지 않다 — 기존 목록 API에 선택적 파라미터만 추가하는 것이 이 설계의 핵심이다.

### 3. 좌측 패널(사이드바) UI 설계

#### 3.1 결정: 새 패널이 아니라 기존 사이드바 확장
`frontend/src/components/ProjectLayout.tsx`의 `<aside>` 안 `<nav>`는 이미 "대시보드/요구사항/이슈/추적성/테스트케이스/테스트런/릴리스/승인함/설정" `NavLink` 목록을 갖고 있다. **완전히 새로운 패널 레이아웃을 만들지 않고, 이 `<nav>` 안에 신규 컴포넌트 `WorkItemTreePanel`을 "요구사항" 링크와 "이슈" 링크 사이에 삽입**한다. 기존 레이아웃 구조(`<aside>` 폭 240px, 사용자명/로그아웃 하단 고정)는 그대로 유지한다.

#### 3.2 `WorkItemTreePanel` 구조
아코디언(접기/펼치기) 4개 섹션 — PRD / SRS / Defect / TestCase. 각 섹션 헤더에 해당 유형의 전체 건수를 작은 뱃지로 표시.

- **PRD / SRS 섹션**: 같은 `requirements` 트리를 `requirementLevel` 필터만 다르게 적용해 보여주는 **동일한 트리 컴포넌트**를 재사용한다. 펼치면 `rootOnly=true&requirementLevel={PRD|SRS}`로 루트 노드만 먼저 가져오고, 각 노드의 `▸`를 클릭하면 `GET .../requirements/{id}/children`(기존 API)으로 자식을 지연 로딩한다. 노드 클릭 시 `/projects/:id/requirements/:reqId`(기존 상세 라우트)로 이동.
- **Defect 섹션**: `GET .../issues?type=BUG`(기존 API)로 가져온 **플랫 목록**(이슈는 계층이 없으므로 트리 아님) 상위 N건(예: 10건) + "+N개 더보기 → 이슈 목록으로" 링크(`/projects/:id/issues?type=BUG`로 이동, 기존 필터 재사용).
- **TestCase 섹션**: `GET .../test-cases`(기존 API)로 가져온 플랫 목록 상위 N건 + "전체 보기 → 테스트케이스 목록" 링크.
- **표시 대상**: 세 섹션 모두 프로젝트에 속한 데이터 전체(멤버 전원이 생성한 것)를 그대로 보여준다 — 담당자/작성자 필터를 추가하지 않는다(제품 오너 확정 사항 #3).

#### 3.3 성능/스코프 제한 (의도적)
- 사이드바에 전체 트리를 한 번에 그리지 않는다 — **루트만 먼저 로드하고 펼칠 때 자식을 지연 로딩**하는 아코디언으로 범위를 한정한다. 대규모 프로젝트에서 사이드바가 느려지는 것을 방지하기 위한 의도적 제한(Light 철학).
- 아코디언 펼침/접힘 상태를 서버에 저장하거나 사용자별로 영속화하는 기능은 이번 범위에 포함하지 않는다(필요해지면 `localStorage` 수준의 가벼운 개선으로 후속 처리).
- "+ 새 PRD 만들기" 같은 유형별 바로가기 생성 버튼은 **선택 사항**으로 남긴다 — 1차 구현에서는 생략하고 기존 "새 요구사항" 생성 폼에 `requirementLevel` 선택 필드를 추가하는 것으로 충분하다(과설계 방지).

#### 3.4 요구사항 생성/수정 폼 보완
기존 요구사항 생성/수정 폼(05-frontend.md §5.2)에 `requirementLevel`(PRD/SRS) 선택 필드를 추가한다. **기본값 추천 로직(프론트 전용, 백엔드 강제 없음)**: 상위 요구사항(`parentRequirementId`)을 선택하지 않았으면 `PRD`를, 선택했으면 `SRS`를 기본값으로 미리 채워주되 사용자가 자유롭게 변경할 수 있다 — 이 추론은 UX 편의일 뿐이고 서버는 어떤 조합이든 그대로 저장한다(§1.1의 "상하 관계 강제하지 않음" 결정과 일치).

## 결과 (Consequences)

### 장점
- 신규 테이블 0개, 신규 `TargetType` 값 0개, 신규 컨트롤러 0개 — 기존 인프라(`traceability_links`, `parent_requirement_id`, `issues.type`, `PolymorphicTargetValidator`)를 100% 재사용한다.
- API 변경이 전부 "선택적 파라미터 추가" 수준이라 기존 호출자(현재 프론트, 향후 생길 수 있는 다른 클라이언트)에 영향이 없다.
- 구현 리스크가 작아 Phase 단위로 빠르게 쪼개 진행할 수 있다(예: 1단계 DB+API, 2단계 사이드바 UI).

### 단점 / 리스크
- **두 분류축 공존으로 인한 사용자 혼동**: 요구사항 생성 폼에 `type`(FUNCTIONAL/NON_FUNCTIONAL/BUSINESS)과 `requirementLevel`(PRD/SRS) 두 드롭다운이 나란히 보이게 된다 — 라벨/도움말 문구로 명확히 구분해야 하며, 구현 시 사용자 테스트(또는 적어도 qa-tester 리뷰)로 혼동 여부를 확인할 것을 권장한다.
- **`traceability_links.source_type` CHECK 완화의 하류 영향**: 기존에 "source_type은 항상 REQUIREMENT 또는 ISSUE"라고 암묵적으로 가정한 코드(프론트 타입 분기, 백엔드 서비스 로직)가 있다면, `TEST_CASE`가 source로 들어오는 경우를 처리하지 못할 수 있다 — developer는 구현 전 `TraceabilityLinkService` 및 관련 프론트 컴포넌트에서 이 가정이 있는지 확인해야 한다. 데이터 자체의 하위 호환성은 문제없다(기존 행은 전부 제약 완화 전 값).
- **PRD/SRS 계층의 자유도로 인한 일관성 저하 가능성**: 상하 관계를 강제하지 않기로 결정했으므로, 팀마다 SRS를 PRD의 자식으로 쓰거나 반대로 쓰거나 아예 섞어 쓸 수 있어 트리 그룹핑이 팀마다 다르게 보일 수 있다 — 이는 제품 오너가 "위아래 구분은 없지만 사용자 판단"이라고 명시적으로 요청한 자유도이므로 **의도된 트레이드오프**이며 버그가 아니다.
- **사이드바 공간 제약**: 기존 8개 내비게이션 링크에 4개 아코디언이 추가되면 세로 공간이 빡빡해질 수 있다 — 1차 구현에서는 기본적으로 모든 아코디언을 접힌 상태로 시작하는 것으로 완화하고, 추가 개선(펼침 상태 기억 등)은 후속 과제로 남긴다.
- **옵션 2를 선택하지 않은 이유(재정리)**: `WorkItem` 상위 모델로의 재설계는 16개 기존 엔티티와 Phase 0~15 전체 코드에 영향을 주는 큰 구조 변경이다. 지금 요구되는 것은 사이드바에서의 그룹핑 조회와 자유로운 상호 연결일 뿐이고, 이는 이미 존재하는 `traceability_links`/`parent_requirement_id`로 충분히 해결된다 — 구조 변경의 이익이 비용을 정당화하지 못한다고 판단했다.

### `01-scope.md` 반영 판단 (재확인)
이 ADR은 `01-scope.md` §1.3의 비스코프 항목과 충돌하지 않으며, §1.2에 이미 있는 기존 bullet(요구사항/이슈/테스트케이스/추적성)의 세부 구현 범위로 볼 수 있어 **스코프 확장 승인이 필수는 아니라고 판단한다.** 다만 추적성을 위해 §1.2의 관련 bullet 옆에 "(사이드바 유형별 트리 뷰 포함, ADR-013)" 정도의 한 줄 참조를 추가하는 것을 권장하되, 이 판단과 반영 여부는 오케스트레이터/제품 오너에게 맡긴다 — 이번 작업에서 `01-scope.md`를 직접 수정하지 않았다.

### 구현 전 반영이 필요한 설계 문서 (이번 작업 범위에는 포함하지 않음)
- `03-data-model.md` §3.4(requirements 테이블에 `requirement_level` 컬럼 추가)·§3.6(`traceability_links.source_type` CHECK 갱신 서술)
- `04-api.md` §4.5(요구사항 목록 API에 `requirementLevel`/`rootOnly` 쿼리 파라미터 추가)
- `05-frontend.md` §5.1(사이드바 설명)·§5.2(요구사항 생성 폼 필드 추가)·신규 §5.x(`WorkItemTreePanel` 상세 설계)
- `GLOSSARY.md` §1(`RequirementLevel` 개념)·§3(`RequirementLevel` enum: `PRD`,`SRS`)·§6(`WorkItemTreePanel` 화면 용어)

### developer에게 위임할 구현 범위 (승인 후)
1. 마이그레이션: `requirements.requirement_level` 컬럼+CHECK(DEFAULT 'SRS' 백필), `traceability_links.source_type` CHECK에 `TEST_CASE` 추가
2. 백엔드: `CreateRequirementRequest`/`UpdateRequirementRequest`에 `requirementLevel` 필드 추가, 목록 조회 서비스에 `requirementLevel`/`rootOnly` 필터 추가
3. 프론트: `WorkItemTreePanel` 컴포넌트 신설, `ProjectLayout.tsx`에 통합, 요구사항 생성/수정 폼에 PRD/SRS 선택 필드(+ 기본값 추천 로직) 추가
4. qa-tester 검증: (a) `requirementLevel`/`rootOnly` 파라미터 없이 호출한 기존 목록 API가 완전히 동일하게 동작하는지(회귀), (b) `source_type='TEST_CASE'`로 신규 링크 생성이 실제로 가능해졌는지 + 기존 `TraceabilityLinkService`/프론트 로직이 이 값을 깨지지 않고 처리하는지, (c) 사이드바 4개 아코디언이 프로젝트 멤버 전원의 데이터를 "내가 만든 것" 필터 없이 보여주는지
