# ADR-015: 권한 체계 정리 — 역할 표시명 변경, 회원가입·라이센스 제거, 마지막 System Admin 보호, 프로젝트 생성 System Admin 전용화

> **[2026-10-05 제품 오너 결정 반영]** 처음 작성할 때 "확인 필요"로 남긴 P1~P4를 제품 오너가 모두 결정했다. P1·P2·P3는 이 ADR의 제안대로 확정됐다. **P4는 제안(현행 유지)과 반대로 "프로젝트 생성은 System Admin 전용"으로 결정**되어 D6과 상세 설계 §5를 추가했다.

## 맥락 (Context)

### 제품 오너 요청 (2026-10-05, 원문 그대로)

> "계정생성자체를 system_admin이 할수있게해주고 system_admin권한은 global에서 사용가능한 권한으로써 admin아이디를 가진사용자와 admin이 직접 다른사용자에게도 권한을 부여할수있어야한다. 그리고 각 project별로 project_admin이 별도로 존재해야하며 project_admin은 project에 대한 모든 설정이 가능하고 project_assignable 권한을 가진 사용자는 읽기+쓰기가 가능하고 project_user를 가진 사용자는 읽기만 가능해야한다. project단의 권한은 project_admin이 줄수있고 system_admin의경우 위 권한을 모두 가진다."

같은 날 제품 오너가 추가로 고른 선택지:

1. 권한 이름은 **화면 표시명만** 바꾼다. DB/코드 값은 그대로 둔다.
2. 회원가입(self-signup)과 라이센스 파일 기능은 **둘 다 제거**한다. ADR-011을 대체(Superseded)한다.
3. **마지막 활성 System Admin을 보호**한다. 활성(`enabled=true`) `ADMIN`이 1명뿐이면 그 사람의 `ADMIN`을 해제하거나 비활성화하는 요청을 400으로 거부한다. 아이디가 `admin`인 계정이라고 따로 취급하지 않는다.
4. (2026-10-05 추가 결정) **프로젝트 생성은 System Admin만** 한다. 리뷰 결정 기록 예외(P1)와 Project Assignable 쓰기 범위(P2)는 현행 유지로 확정한다. 워크플로우 최소 역할 처리(P3)는 이 ADR의 제안대로 확정한다.

### 역할별 쓰기 권한 확인 결과 (`ProjectMemberService.requireRole` 호출부 전수 grep)

- **`VIEWER`로 통과하는 메서드**: 전부 `@Transactional(readOnly = true)` 조회 메서드다(Requirement/Issue/TestCase/TestRun/Release/Traceability/Comment/GitLink/JenkinsBuild/Dashboard/AuditLog `listForTarget`/ProjectMember `list`/Project `get`/CustomField `listActive`·`listValues`/FormLayout `getForRender`/Enumeration `listActiveValues`/Workflow `nextStatuses`/ReviewCycle `listForTarget`/Baseline `list`·`get`·`diffAgainstCurrent`).
  - **유일한 예외**: `ReviewCycleCommandService.recordMyDecision()`(`PATCH /api/projects/{projectId}/review-cycles/{cycleId}/participants/me`)이 `VIEWER`로 쓰기를 허용한다. 단, 이 메서드는 **해당 사이클의 참여자로 지정된 본인만** 쓸 수 있다(참여자가 아니면 역할과 무관하게 403). 쓰는 대상도 `review_participants`의 본인 행(decision/comment)뿐이며, 요구사항/이슈의 상태나 내용은 절대 바꾸지 않는다(ADR-008, 03-data-model.md §3.19).
- **`MEMBER+`인 쓰기**: Requirement/Issue/TestCase `create`·`update`·`changeStatus`, Traceability `createLink`·`deleteLink`, Comment `create`·`delete`(남의 댓글 삭제는 추가로 PROJECT_ADMIN 필요), TestRun `create`·`addCases`·`recordResult`·`changeStatus`, GitLink `createManual`·`delete`, JenkinsBuild `triggerBuild`, Approval `create`, Release `addItem`·`removeItem`, ReviewCycle `create`·`close`, CustomFieldValue `saveValues`.
- **`PROJECT_ADMIN+`인 쓰기/조회**: Project `update`·`delete`·`updateGithubIntegration`·`updateJenkinsIntegration`, 멤버 추가/역할 변경/제거, Requirement/Issue/TestCase `delete`, Release `create`·`update`·`changeStatus`, Baseline `create`, Approval `list`·`decide`, AuditLog 프로젝트 전체 `list`, Configuration 4종의 설정 조회·변경 전부.
- **프로젝트 역할 검사가 없는 API**: `POST /api/projects`(인증된 사용자면 누구나 프로젝트 생성 가능, 생성자는 PROJECT_ADMIN이 됨), `GET /api/projects`(멤버인 프로젝트만 보임), 개인 API(`/api/auth/me`, `PUT /api/users/me/password`, 내 작업 대시보드).
- **워크플로우 규칙의 `allowed_role = 'VIEWER'`**: `RequirementService.changeStatus`/`IssueService.changeStatus`가 워크플로우 정책을 보기 **전에** 먼저 `MEMBER+`를 요구한다. 그래서 `VIEWER`로 설정한 규칙은 실제로는 `MEMBER`로 설정한 것과 똑같이 동작한다. VIEWER가 상태를 바꿀 수 있는 경로는 없다(V17 CHECK가 `VIEWER` 값을 허용하고, `WorkflowRuleSettingsTab.tsx`가 "VIEWER+" 옵션을 보여줘서 생기는 오해일 뿐이다).

### 라이센스 기능을 없애도 되는 이유

라이센스 서브시스템(ADR-011)은 "회원가입으로 들어오는 계정 수를 시트 수와 만료일로 제한"하려고 만든 것이다. 계정을 System Admin만 만들 수 있게 되면 계정 수는 관리자가 직접 통제한다. 시트 게이트가 지키던 위협(통제 안 되는 계정 증가)이 사라지므로 라이센스를 남겨둘 이유도 없다. 그대로 두면 오히려 다음 문제만 남는다(CURRENT-STATE §6에 등록된 리스크).
- `LICENSE_SIGNING_SECRET` 기본값이 개발용 평문이다. 기본값을 아는 사람은 누구나 라이센스를 위조할 수 있다.
- 라이센스가 만료되거나 없으면 ADMIN이 아닌 사용자는 전부 로그인할 수 없다. 이때 복구할 방법은 ADMIN 로그인 하나뿐이라, ADMIN이 모두 비활성화되면 복구가 불가능하다.
- 관리자가 계정을 만들 때도 라이센스가 유효해야 한다(게이트 A·B). 라이센스 운영을 따로 하지 않는 지금 환경에서는 계정 생성이 막힐 위험만 있다.

## 결정 (Decision)

### D1. 역할 이름은 화면 표시명만 바꾼다 (DB·코드·API 값은 그대로)

| 구분 | DB/코드/API 값 (변경 없음) | 화면 표시명 (신규) | 의미 |
|---|---|---|---|
| 시스템 역할 | `ADMIN` | **System Admin** | 시스템 전체 관리. 계정 생성/수정/비활성화, System Admin 부여·해제, 시스템 테마. 모든 프로젝트에서 Project Admin 이상으로 취급 |
| 시스템 역할 | `USER` | **User** | 일반 사용자. 프로젝트 권한은 각 프로젝트의 멤버 역할로 결정 |
| 프로젝트 역할 | `PROJECT_ADMIN` | **Project Admin** | 해당 프로젝트의 모든 설정, 멤버/역할 부여, 삭제·릴리스·베이스라인·승인 결정 |
| 프로젝트 역할 | `MEMBER` | **Project Assignable** | 읽기 + 쓰기(작업 항목 생성·수정·상태 변경 등). 설정 변경 불가 |
| 프로젝트 역할 | `VIEWER` | **Project User** | 읽기 전용 (예외: 아래 P1) |

값을 바꾸지 않는 이유:
- 공용 DB(`ALM_Project`)를 KPI 집계 도구가 직접 읽는다(ADR-002, CURRENT-STATE §3). 값을 바꾸면 그 도구의 쿼리가 깨진다.
- `chk_users_system_role`(V1), `chk_project_members_role`(V1), `chk_workflow_transition_rules_allowed_role`(V17) CHECK 제약을 그대로 둘 수 있다. 마이그레이션이 필요 없다.
- API 계약(`systemRole`, `role`, `allowedRole` 값)이 그대로라서 기존 클라이언트와 테스트에 영향이 없다.

적용 규칙:
- 표시명 매핑은 프론트엔드 **한 곳**에만 둔다(예: `frontend/src/auth/roleDisplayName.ts`. 정확한 파일명은 developer가 `02-naming-spring-react.md`에 맞춰 정함). 화면에서 역할 값(`'ADMIN'`, `'MEMBER'` 등)을 그대로 출력하지 않는다. `<option value="MEMBER">`처럼 **value는 원래 값**을 쓰고 라벨에만 표시명을 쓴다.
- 문서/코드 식별자(클래스, 메서드, 04-api.md의 `[MEMBER+]` 같은 권한 표기)는 기존 값을 계속 쓴다. 04-api.md §4.1 권한 표기 설명과 GLOSSARY.md §3에 매핑을 한 번 적어 연결한다.
- 동음이의 주의: 시스템 역할 `USER`("User")와 프로젝트 역할 `VIEWER`("Project User")는 다른 개념이다. GLOSSARY.md에 이 점을 명시한다.

### D2. 회원가입·라이센스 기능을 제거한다 (ADR-011 Superseded)

- 계정은 **System Admin만** `POST /api/users`로 만든다. 공개된 계정 생성 경로는 없다.
- 라이센스 업로드/조회 API·화면, 로그인 및 계정 생성 시의 라이센스 게이트, `LICENSE_SIGNING_SECRET` 설정을 모두 제거한다.
- **DB는 건드리지 않는다.** `licenses` 테이블(V9)은 DROP하지 않고 사용만 중단한다(공용 DB 데이터 보존). `audit_logs.target_type` CHECK에 들어 있는 `'LICENSE'`(V10)도 그대로 둔다.
- **Java enum `AuditTargetType.LICENSE`는 남긴다.** 이미 `audit_logs`에 `target_type='LICENSE'` 행(과거 라이센스 업로드 기록)이 있을 수 있다. 상수를 지우면 그 행을 JPA로 읽을 때 enum 변환 오류가 난다. 새로 기록하는 곳만 없어진다.

### D3. 마지막 활성 System Admin을 보호한다

- 불변식: **`enabled = true`이고 `system_role = 'ADMIN'`인 사용자가 항상 1명 이상 있어야 한다.**
- 이 불변식을 깨는 요청(대상이 유일한 활성 ADMIN인데 ADMIN을 해제하거나 비활성화하는 요청)은 `400 LAST_ACTIVE_ADMIN`으로 거부한다.
- 아이디 `admin`(V2 시드)은 특별 취급하지 않는다. 다른 활성 ADMIN이 있으면 `admin`도 ADMIN 해제나 비활성화가 가능하다.
- 동시성은 **비관적 락**(`SELECT ... FOR UPDATE`)으로 처리한다(상세 설계 §3.4).

### D4. 권한 정책 확정 (코드 확인 중 나온 애매한 부분 — 2026-10-05 제품 오너 결정 완료)

- **P1. [확정 — 제품 오너 결정 2026-10-05] Project User(VIEWER)의 리뷰 결정 기록은 예외로 허용한다(현행 유지).** 이유: (a) 리뷰 참여자는 Project Assignable 이상이 지정한 사람이다. (b) 쓰는 것은 "내 의견(승인/반려/의견만 + 코멘트)"뿐이고 작업 항목 데이터는 바꾸지 않는다(리뷰 사이클은 기록 전용, 01-scope.md §1.3). (c) 읽기 전용 검토자에게 의견을 받는 것이 리뷰 사이클을 만든 목적에 맞다. 이 예외는 06-auth.md와 04-api.md §4.17에 "Project User가 쓸 수 있는 유일한 API"로 명시한다. 코드 변경은 없다.
- **P2. [확정 — 제품 오너 결정 2026-10-05] Project Assignable(MEMBER)의 쓰기 범위는 현행 그대로 둔다. 코드 변경 없음.** 요구사항/이슈/테스트케이스 **삭제**, 릴리스 생성·수정·상태 변경, 베이스라인 생성, 승인 결정은 계속 Project Admin 전용이다. 이것들은 프로젝트 이력과 기준선을 관리하는 행위로 보고 "프로젝트 설정/관리"(Project Admin) 쪽에 둔다. 요청의 "읽기+쓰기"는 작업 항목 생성·수정·상태 변경 수준으로 해석한다.
- **P3. [확정 — 제품 오너 결정 2026-10-05] 워크플로우 규칙의 `allowed_role = 'VIEWER'`**: DB 값과 API 입력은 계속 허용한다(V17 CHECK, 하위 호환). 다만 화면의 "최소 역할" 드롭다운에서는 새로 고를 수 있는 옵션에서 VIEWER를 뺀다. 이미 VIEWER로 저장된 규칙은 "Project User+ (실제로는 Project Assignable+와 동일)"로 표시한다. 이유: Project User는 읽기 전용이라 상태 전이를 할 수 없기 때문이다(`changeStatus`의 `MEMBER+` 사전 검사).
- **P4. [확정 — 제품 오너 결정 2026-10-05] 프로젝트 생성은 System Admin 전용으로 바꾼다.** 이 ADR 초안은 "현행 유지"를 제안했지만 제품 오너가 제한하기로 결정했다. 설계는 D6과 상세 설계 §5에 있다.

### D6. 프로젝트 생성은 System Admin 전용 (P4 결정)

- `POST /api/projects`에 `@PreAuthorize("hasRole('ADMIN')")`를 붙인다. ADMIN이 아니면 `403 FORBIDDEN`(ADR-014에서 추가한 `GlobalExceptionHandler.handleAccessDenied` 경로)을 받는다.
- **생성자 자동 등록은 현행 그대로 둔다.** `ProjectService.create()`는 지금처럼 요청한 사용자(=System Admin)를 그 프로젝트의 `PROJECT_ADMIN` 멤버로 등록한다. 실제 담당 Project Admin은 프로젝트를 만든 뒤 기존 멤버 탭(`POST /api/projects/{id}/members`)에서 지정한다.
- 요청에 `projectAdminUserId` 같은 새 필드는 **추가하지 않는다**. 이유:
  - (a) `CreateProjectRequest`, 서비스, 프론트 폼을 바꿀 필요가 없어 변경이 가장 작다.
  - (b) 담당자 지정은 이미 있는 멤버 관리 API/화면으로 할 수 있어 기능이 겹친다.
  - (c) 새 필드를 넣으면 "지정한 사용자가 존재하는지/활성인지" 검증과 에러 코드를 새로 설계해야 한다.
  - System Admin은 어차피 모든 프로젝트에서 Project Admin 이상으로 취급되므로(`requireRole`), 자동 등록된 멤버 행은 권한상 중복이다. 하지만 해가 없고 멤버 목록에 "누가 만들었는지"가 남는다는 장점이 있다. 필요 없으면 생성 후 멤버 탭에서 제거해도 된다.
- 기존 프로젝트와 기존 `project_members` 행은 그대로 둔다. 데이터 이전이 없고 스키마 변경도 없다(D5 유지).

### D5. 스키마 변경 없음 (V19 만들지 않음)

표시명 변경은 프론트엔드에서만 처리한다. 기능 제거도 테이블/제약을 그대로 둔다. 프로젝트 생성 제한(D6)은 어노테이션 하나로 처리한다. 마지막 ADMIN 보호는 애플리케이션 레벨 검사와 행 락으로 처리하고, DB 트리거나 제약은 추가하지 않는다. 따라서 **새 Flyway 마이그레이션이 필요 없다.** 기존 V1~V18은 그대로 둔다.

DB 트리거를 쓰지 않는 이유: 이 프로젝트는 지금까지 비즈니스 규칙을 서비스 레이어에 두었고 DB에는 CHECK/FK/부분 유니크 인덱스만 썼다. 공용 DB에 트리거를 추가하면 같은 DB를 쓰는 다른 도구가 예상하지 못한 동작이 생긴다. `users`의 `system_role`/`enabled`를 바꾸는 쓰기 경로는 `UserService` 하나뿐이다. 다만 `psql`로 직접 UPDATE하는 경우는 막지 못한다(아래 "결과" 리스크).

### 3. 마지막 활성 System Admin 보호 (D3)

#### 3.1 보호 대상 요청

"대상 사용자를 활성 ADMIN 집합에서 빠지게 하는 요청"만 검사한다.

| API | 검사하는 조건 (요청 기준) | 검사 생략 |
|---|---|---|
| `PUT /api/users/{id}` | `request.systemRole != null && request.systemRole != ADMIN` (ADMIN 해제) **또는** `request.enabled == FALSE` (비활성화) | 위 둘 다 아니면 생략(email/fullName만 바꾸거나, `systemRole=ADMIN` 유지, `enabled=true` 등) |
| `DELETE /api/users/{id}` (soft: `enabled=false`) | 항상 검사 | — |
| `POST /api/users` | 해당 없음(활성 ADMIN을 줄이지 않음) | — |

검사할 때 대상이 **현재 활성 ADMIN이 아니면**(USER이거나 이미 비활성인 ADMIN) 그대로 통과한다. 본인에게 하는 요청(자기 ADMIN 해제, 자기 비활성화)도 같은 규칙을 적용한다.

#### 3.2 판정 규칙

```
lockedAdmins = 활성 ADMIN 전체 (행 락 획득, id 오름차순)
if (target.id ∉ lockedAdmins)      → 통과 (대상이 활성 ADMIN이 아님)
if (lockedAdmins.size() <= 1)      → 400 LAST_ACTIVE_ADMIN
else                               → 통과 (변경 후에도 활성 ADMIN이 1명 이상 남음)
```

대상이 활성 ADMIN인지는 이미 로드된 `User` 엔티티 필드가 아니라 **락을 걸고 조회한 결과에 들어 있는지**로 판단한다. 영속성 컨텍스트에 먼저 올라온 엔티티는 동시 트랜잭션이 커밋한 최신 값이 아닐 수 있기 때문이다.

#### 3.3 시나리오

| 상황 | 결과 |
|---|---|
| 활성 ADMIN = {admin}. admin이 자기 ADMIN 해제 / 자기 비활성화 / 다른 ADMIN이 DELETE | 400 `LAST_ACTIVE_ADMIN` |
| 활성 ADMIN = {admin, kim}. kim이 admin의 ADMIN 해제 | 200 (`admin` 아이디도 특별 취급 안 함) |
| 활성 ADMIN = {admin}, 비활성 ADMIN = {lee}. admin 비활성화 | 400 (lee는 비활성이라 세지 않음). 먼저 lee를 `enabled=true`로 바꾸면 그다음엔 허용 |
| 활성 ADMIN = {admin}. admin의 email/fullName만 수정 | 200 (검사 생략) |
| 활성 ADMIN = {admin, kim}. admin과 kim이 **동시에** 서로를 강등 | 한쪽만 200, 다른 쪽은 400 (§3.4) |

#### 3.4 동시성 처리 — 비관적 락

`UserRepository`에 추가:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select u from User u where u.systemRole = com.lightalm.domain.SystemRole.ADMIN and u.enabled = true order by u.id")
List<User> findEnabledAdminsForUpdate();
```

PostgreSQL에서는 `SELECT ... WHERE system_role='ADMIN' AND enabled=true ORDER BY id FOR UPDATE`가 된다.

동작(기본 격리 수준 READ COMMITTED):
1. T1(kim이 admin을 강등)과 T2(admin이 kim을 강등)가 동시에 들어온다.
2. T1이 먼저 {admin, kim} 행 락을 잡는다. T2는 같은 행에서 대기한다.
3. T1이 size 2를 확인하고 admin을 USER로 바꾼 뒤 커밋한다.
4. T2가 락을 얻는다. PostgreSQL은 기다린 행의 **최신 버전으로 WHERE를 다시 평가**한다. admin은 더 이상 ADMIN이 아니어서 빠지고 결과는 {kim}이다. kim이 대상이고 size가 1이므로 400.

`ORDER BY id`로 두 트랜잭션이 항상 같은 순서로 락을 잡게 해 데드락을 막는다.

다른 대안을 고르지 않은 이유:
- **count 조건부 UPDATE** (`UPDATE users SET ... WHERE id=? AND (SELECT count(*) ...) > 1`): READ COMMITTED에서는 서브쿼리가 다른 트랜잭션의 커밋 안 된 변경을 보지 못한다. 서로 다른 행을 고치는 두 UPDATE가 둘 다 count=2를 보고 모두 성공할 수 있어서 **경쟁 상태를 막지 못한다.**
- **SERIALIZABLE 격리**: 직렬화 실패 시 재시도 로직이 필요해서 더 복잡하다.
- **PostgreSQL advisory lock**: DB 고유 기능이라 코드를 읽는 사람이 의도를 파악하기 어렵다. 락 대상인 활성 ADMIN이 보통 몇 명뿐이라 행 락 비용도 무시할 수 있다.

조건: 이 조회와 이어지는 변경은 반드시 `UserService.update()`/`deactivate()`의 같은 `@Transactional` 안에서 실행해야 한다. 검사가 필요 없는 요청(§3.1 "검사 생략")에서는 락 쿼리를 실행하지 않아 일반 수정에 락 부담이 없다.

#### 3.5 에러 응답

| HTTP | `error` | `message` (예시) |
|---|---|---|
| 400 | `LAST_ACTIVE_ADMIN` | `"활성 상태인 System Admin이 최소 1명은 있어야 합니다. 다른 사용자에게 System Admin 권한을 먼저 부여하세요."` |

범용 `VALIDATION_ERROR` 대신 전용 코드를 쓰는 이유는, 프론트엔드가 이 상황을 구분해 안내할 수 있게 하기 위해서다. 400을 쓰는 이유는 제품 오너가 지정했기 때문이다(현재 상태와 충돌하는 요청이라 409도 가능하지만, 이 프로젝트에는 409 선례가 없고 비즈니스 규칙 위반은 모두 400으로 통일되어 있다).

| `com.lightalm.exception.GlobalExceptionHandler` | `handleLastActiveAdminRemoval` | 400 `LAST_ACTIVE_ADMIN` |

`UserService` 자체를 기능 패키지로 옮기거나 `@Setter`를 없애는 리팩터링은 하지 않는다(docs/CLAUDE.md "기존 코드에 대한 예외").

#### 3.7 프론트엔드

`AdminUsersPage.tsx`의 `roleMutation`/`deactivateMutation`은 지금 실패해도 아무것도 표시하지 않는다. 실패 시 서버 `message`를 화면 상단에 표시한다(최소한 `LAST_ACTIVE_ADMIN`은 반드시 사용자에게 보여야 함). 역할 드롭다운은 실패하면 원래 값으로 되돌아가야 한다(쿼리 무효화로 재조회). 마지막 ADMIN의 버튼이나 드롭다운을 미리 비활성화하는 것은 선택 사항이다. 최종 판정은 항상 서버가 한다.

### 4. 하위 호환성 영향

| 대상 | 영향 |

#### 5.3 운영상 주의
- 이제 ADMIN이 아닌 사용자는 프로젝트를 만들 수 없다. 프로젝트가 필요하면 System Admin에게 요청하고, System Admin이 만든 뒤 멤버 탭에서 담당자를 Project Admin으로 추가하는 순서로 운영한다.
- System Admin이 만든 프로젝트마다 그 System Admin의 `PROJECT_ADMIN` 멤버 행이 생긴다. 나중에 그 사람의 System Admin이 해제되어도 이 멤버 행 때문에 해당 프로젝트의 Project Admin 권한은 남는다. 필요하면 멤버 탭에서 제거한다(D6 근거 참고).

## 결과 (Consequences)

### 장점
- 계정 생성 경로가 `POST /api/users`(System Admin) 하나뿐이다. "계정 생성은 System Admin만"이라는 요구를 구조적으로 보장한다.
- CURRENT-STATE §6의 리스크 2건이 기능 제거로 **해소**된다.
  - `LICENSE_SIGNING_SECRET` 기본값 평문 → 라이센스 위조 가능 리스크: 설정 자체가 없어진다.
  - 라이센스 만료 + 모든 ADMIN 비활성 시 복구 불가 리스크: 라이센스 게이트가 없어지고, 대신 D3로 "활성 ADMIN 0명" 상태 자체를 애플리케이션이 막는다.
- 라이센스 관련 코드 약 22개 파일과 테스트 5개가 빠져서 유지보수 면적이 줄어든다.
- 역할 값은 바꾸지 않고 표시명만 바꾸므로 DB, 공용 DB를 읽는 KPI 도구, API 계약 모두 영향이 없다.
- 계정 생성과 프로젝트 생성이 모두 System Admin에게 모인다. "system_admin은 전역 권한, project_admin은 프로젝트 단위 권한"이라는 요청 구조가 명확해진다.

### 단점 / 리스크
- **ADR-011 작업 폐기**: 구현과 qa 검증까지 끝난 기능(2026-10-03)을 2일 만에 제거한다. `licenses` 테이블과 `audit_logs`의 LICENSE 행은 공용 DB에 쓰이지 않는 데이터로 남는다. 나중에 완전히 정리(DROP)하려면 별도 ADR과 새 마이그레이션이 필요하고, 그 전에 다른 도구가 이 테이블을 읽는지 확인해야 한다.
- **DB 직접 수정은 막지 못함**: 마지막 ADMIN 보호는 애플리케이션 레벨이다. `psql` 등으로 `users`를 직접 UPDATE하면 활성 ADMIN이 0명이 될 수 있다. 이 경우 복구도 DB 직접 UPDATE(`UPDATE users SET enabled=true, system_role='ADMIN' WHERE username=...`)로만 가능하다. 운영 문서에 이 복구 절차를 남긴다.
- **기존 세션은 즉시 반영 안 됨(기존부터 있던 한계, 범위 밖)**: `UserPrincipal`은 로그인할 때 세션에 저장된다. 그래서 ADMIN이 해제되거나 비활성화된 사용자도 **세션이 끝날 때까지** 이전 권한을 유지한다. 마지막 ADMIN 보호는 DB 상태 기준이라 이 한계와는 별개다. 즉시 반영이 필요하면 별도 ADR(세션 무효화 또는 요청마다 사용자 상태 재조회)이 필요하다.
- **활성 ADMIN이 1명인 운영 환경**: 운영 DB에 활성 ADMIN이 `admin` 하나뿐이면, 배포 후 이 계정의 비활성화나 강등이 막힌다(의도된 동작). 담당자 교체 시에는 새 사용자에게 먼저 System Admin을 준 뒤 기존 계정을 해제하는 순서로 운영해야 한다.
- **표시명과 문서 표기 이원화**: 화면은 "Project Assignable", 문서·API는 `MEMBER`를 계속 쓴다. GLOSSARY.md 매핑표가 하나뿐인 대응 근거이므로 반드시 갱신해야 한다.
- **프로젝트 생성 제한(하위 호환 변경)**: 지금까지 USER가 직접 만들던 흐름이 403으로 막힌다. 프로젝트를 만들 때마다 System Admin을 거쳐야 하므로 운영 부담이 늘어난다(제품 오너가 의도한 통제). System Admin이 만든 프로젝트에는 그 System Admin이 Project Admin 멤버로 자동 등록된다(§5.3).
- **비관적 락**: 활성 ADMIN 행을 잠깐 잠근다. 이 행들을 동시에 수정하는 다른 경로(예: 로그인)는 `users`를 읽기만 하므로 막히지 않는다. ADMIN의 email/fullName 수정은 검사 생략 경로라 락을 잡지 않는다. 영향은 무시할 수 있는 수준이다.

## 검증 (DoD) — qa-tester 판정 항목

**제거 확인**
1. `POST /api/auth/signup` 비인증 호출 → 401 또는 403(CSRF 토큰 유무에 따라 다름. 2xx가 아니면 통과), `users` 행이 생기지 않음.
2. `GET /api/public/license-status` 비인증 호출 → 401. `/api/admin/licenses`, `/api/admin/licenses/current` ADMIN 호출 → 200이 아님(핸들러 없음).
3. `licenses` 테이블에 `ACTIVE` 행이 없거나 만료된 상태에서, ADMIN이 아닌 사용자 로그인 → 200 + `UserResponse`(라이센스 게이트 없음).
4. 같은 상태에서 ADMIN의 `POST /api/users` → 201(라이센스/시트 게이트 없음).
5. `backend/src/main`과 `frontend/src`에서 `License`/`Signup`/`signup`/`license-status`/`LICENSE_SIGNING_SECRET` grep → 0건. 예외: `AuditTargetType.LICENSE` 1건과 주석 없음.
6. Flyway: 새 마이그레이션 없음(V18이 최신), 기존 DB에서 애플리케이션 정상 기동(`ddl-auto: validate` 통과). `licenses` 테이블과 데이터가 그대로 남아 있음.
7. 프론트: `/login`에 회원가입 링크 없음, TopNavbar에 "라이센스 관리" 링크 없음, `/signup`·`/admin/licenses` 라우트 없음. `npx tsc -b`, `npm run build`, `npm run lint` 통과(새 경고 0건).

**표시명 확인**
8. 사용자 관리 화면 역할 드롭다운 라벨이 "User"/"System Admin", 프로젝트 설정 멤버 탭이 "Project Admin"/"Project Assignable"/"Project User". 저장 요청 본문 값은 여전히 `ADMIN`/`USER`/`PROJECT_ADMIN`/`MEMBER`/`VIEWER`(네트워크 탭 확인).
9. 워크플로우 탭 최소 역할 드롭다운에 새로 고를 수 있는 VIEWER 옵션이 없음. 기존 `allowedRole=VIEWER` 규칙은 정상 표시.

**마지막 ADMIN 보호**
10. 활성 ADMIN 1명일 때 그 사용자에게 `PUT {systemRole:"USER"}`, `PUT {enabled:false}`, `DELETE`를 각각 보내면 400 `LAST_ACTIVE_ADMIN`이 나오고 DB 값은 그대로.
11. 활성 ADMIN 2명일 때 `admin`(시드 계정)의 ADMIN 해제 → 200. 그 직후 남은 1명의 해제 → 400.
12. 대상이 USER이거나 비활성 ADMIN이면 검사 없이 기존 동작(200/204).
13. 활성 ADMIN 1명의 email/fullName만 수정 → 200.
14. 동시성: 활성 ADMIN 2명이 서로를 동시에 강등하는 요청 2개를 병렬로 보냄 → 정확히 1건만 성공, 이후 활성 ADMIN 수 = 1. 단위 테스트(Mockito)로 판정 분기를 검증하고, 실제 락 동작은 로컬 docker-compose Postgres에서 두 세션을 열어 수동 확인(이 환경은 Testcontainers 실행 불가, CURRENT-STATE §6). 가능하면 `*IT.java`로 작성해 Docker 정상 환경에서 `mvn verify`로 실행.
15. 사용자 관리 화면에서 400이 나면 서버 메시지가 표시되고 드롭다운이 원래 값으로 돌아감.

**프로젝트 생성 System Admin 전용 (D6)**
16a. USER(어떤 프로젝트의 PROJECT_ADMIN이라도) 계정의 `POST /api/projects` → 403 `FORBIDDEN`, `projects` 행이 생기지 않음.
16b. ADMIN의 `POST /api/projects` → 201. 그 ADMIN이 새 프로젝트의 `project_members`에 `PROJECT_ADMIN`으로 등록됨. 이후 멤버 탭에서 다른 사용자를 Project Admin으로 추가 가능.
16c. 이전에 USER가 만든 기존 프로젝트의 멤버와 역할이 그대로이고, 그 Project Admin이 수정·멤버 관리를 계속 할 수 있음.
16d. 프론트: ADMIN이 아니면 프로젝트 목록에 "새 프로젝트" 버튼이 없고, `/projects/new`에 직접 들어가면 `/`로 리다이렉트됨. ADMIN은 버튼이 보이고 생성할 수 있음.
16e. `@PreAuthorize` 권한 테스트(ADR-014 `ThemeAdminControllerAuthorizationTest` 방식)로 `ProjectController.create`의 ADMIN 허용/USER 거부를 단위 수준에서 검증.

**회귀**
16. `mvnw test` 전체 통과(삭제한 라이센스/가입 테스트를 빼고 신규 테스트를 더한 개수를 기록). 기존 프로젝트 권한 동작(VIEWER 쓰기 403, MEMBER 설정 변경 403, ADMIN 전 프로젝트 통과) 변화 없음.
17. 권한 없는 사용자의 `@PreAuthorize` 거부가 여전히 403(ADR-014 수정 회귀 확인. `GlobalExceptionHandler`를 손대므로).

## developer에게 위임할 구현 범위

1. 백엔드 제거: §1.1 파일 22개, §1.2 테스트 5개 삭제. §1.3 기존 파일 수정(SecurityConfig, JsonAuthenticationSuccessHandler, UserService, GlobalExceptionHandler, UserRepository, application.yml, 주석 3곳). `AuditTargetType.LICENSE`는 유지.
2. 마지막 ADMIN 보호: `com.lightalm.user.service.SystemAdminRetentionPolicy`, `com.lightalm.user.domain.LastActiveAdminRemovalException`, `UserRepository.findEnabledAdminsForUpdate()`, `UserService.update()/deactivate()` 연결, `GlobalExceptionHandler` 400 `LAST_ACTIVE_ADMIN`. 단위 테스트(`SystemAdminRetentionPolicyTest`, `UserServiceTest` 신규. 현재 `UserService` 테스트가 없음).
3. 프론트 제거: §1.4 파일 4개 삭제, §1.5 파일 수정.
4. 표시명: 역할 표시명 매핑 모듈 1개 + §2 화면 3개 적용, WorkflowRuleSettingsTab VIEWER 옵션 처리(P3), AdminUsersPage 에러 표시(§3.7).
5. 프로젝트 생성 제한(D6, §5): `ProjectController.create()`에 `@PreAuthorize("hasRole('ADMIN')")` 추가(ProjectService·CreateProjectRequest는 변경 없음). `ProjectListPage.tsx`의 "새 프로젝트" 버튼과 빈 목록 안내문을 ADMIN 조건부로 처리. `router.tsx`의 `/projects/new`를 `AdminRoute` 아래로 이동. 권한 테스트 추가(DoD 16e).
6. 마이그레이션 **만들지 않음**.
7. 위 "구현 시 함께 갱신할 문서" 중 architect 담당 항목은 구현 결과(실제 클래스명, 테스트 수)를 architect에게 전달해 같은 작업 안에서 반영. 오케스트레이터 담당 항목은 오케스트레이터에게 알림.
8. `synology` push(운영 배포)는 하지 않는다. 배포 판단은 오케스트레이터가 한다. 배포 전에 운영 DB의 활성 ADMIN 수를 확인할 것을 권고한다(1명이면 배포 후 그 계정은 해제 불가 — 의도된 동작이지만 운영자에게 미리 알려야 함).
