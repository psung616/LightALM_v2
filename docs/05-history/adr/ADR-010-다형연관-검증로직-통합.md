# ADR-010: 다형 연관(target_type, target_id) 검증 로직을 `PolymorphicTargetValidator`로 통합

## 맥락 (Context)

Light ALM은 댓글(Comment), Git 연결(GitLink), Jenkins 빌드(JenkinsBuild), 릴리스 항목(ReleaseItem), 추적성 링크(TraceabilityLink) 5곳에서 `(target_type, target_id)` 형태의 다형 연관을 쓴다. 이 연관은 DB FK 제약 없이 애플리케이션 레벨에서 존재/소속 검증을 한다(`docs/02-design/03-data-model.md` §3.10 참고). 그런데 이 검증 로직이 다음 5개 서비스 메서드에 사실상 동일하게 중복 구현돼 있었다.

- `CommentService.verifyTargetExists` (`backend/src/main/java/com/lightalm/service/CommentService.java:75-89`)
- `GitLinkService.verifyTargetExists` (`GitLinkService.java:223-237`)
- `JenkinsBuildService.verifyTargetExists` (`JenkinsBuildService.java:103-117`)
- `ReleaseService.validateTargetExists` (`ReleaseService.java:174-188`)
- `TraceabilityService.validateTarget` (`TraceabilityService.java:251-265`)

다섯 메서드 모두 `TargetType`이 `REQUIREMENT`면 `requirementRepository`, 아니면(`else`) `issueRepository`로 조회해서 존재 여부와 `project.getId()` 일치 여부를 검증하는 구조다. 다섯 곳 모두 조회된 엔티티 객체 자체는 검증 이후 재사용하지 않고 존재 확인 용도로만 쓴다(호출부 확인 완료). 이 중복이 두 가지 문제를 낳았다.

### 문제 1 — 예외 타입 불일치 (404 vs 400)
Comment/GitLink/Jenkins/Release 4곳은 "대상이 다른 프로젝트 소속"인 경우에도 `ResourceNotFoundException`(404)을 던진다. 반면 `TraceabilityService.validateTarget`만 이 경우 `ValidationException`(400)을 던진다. `GlobalExceptionHandler.java:19-32`에서 `ResourceNotFoundException` → 404, `ValidationException` → 400으로 매핑됨을 확인했다. 문서/주석에 이 차이를 정당화하는 근거가 없어 의도적 설계가 아니라 구현이 갈라지며 생긴 드리프트로 판단된다.

### 문제 2 — `TEST_CASE` 미분기로 인한 잠재 버그
`TargetType` enum은 `REQUIREMENT, ISSUE, TEST_CASE` 3개 값을 갖는다(`domain/TargetType.java`). 그런데 5개 메서드 모두 `if (REQUIREMENT) ... else (ISSUE로 취급)` 구조라 `TEST_CASE`를 구분하지 않고 `issueRepository`로 조회를 시도한다.

- Comment/GitLink/JenkinsBuild: 컨트롤러의 `toTargetType(String pathSegment)`가 URL 경로 세그먼트(`"requirements"`/`"issues"`)만 화이트리스트하고 그 외에는 컨트롤러 자체에서 400을 던지므로, API 경로로는 `TEST_CASE`가 서비스 계층까지 도달하지 않는다(`CommentController.java:49`, `GitLinkController.java:49`, `JenkinsBuildController.java:42` 참고).
- ReleaseService: `addItem()`에서 `validateTargetExists` 호출 전에 `if (targetType != REQUIREMENT && targetType != ISSUE) throw ValidationException(...)` 가드가 이미 있어 안전하다(`ReleaseServiceTest.addItem_rejectsTestCaseTargetType`로 테스트됨).
- **`TraceabilityService`**: `CreateTraceabilityLinkRequest`가 `sourceType`/`targetType`을 `@RequestBody` JSON으로 `TargetType` enum에 직접 바인딩하며(`CreateTraceabilityLinkRequest.java:13-20`), 별도의 화이트리스트 가드가 없다. 클라이언트가 `sourceType: "TEST_CASE"`를 실제로 보낼 수 있고, 이 경우 `issueRepository`로 잘못 조회를 시도하다 "이슈를 찾을 수 없습니다"라는 오해의 소지가 있는 404를 던지는 **살아있는 버그**다.

### 기존 테스트 커버리지
Comment/GitLink/JenkinsBuild/TraceabilityService에는 `*Test.java`가 존재하지 않는다. `ReleaseServiceTest`만 있고 이 검증 로직 관련 테스트는 `addItem_rejectsTestCaseTargetType` 1건뿐이며, 이는 `addItem()`의 호출부 가드만 검증할 뿐 `validateTargetExists` 자체를 검증하지는 않는다.

### 관련 제품 오너 논의
아래 결정 사항은 제품 오너와 이미 논의를 마치고 승인받았다. 이 ADR은 그 결정을 기록하는 문서다.

## 결정 (Decision)

### 새 공용 컴포넌트: `PolymorphicTargetValidator`
- 패키지: `com.lightalm.service.support` (신규 패키지)
- `@Component`로 등록
- 이름을 "Resolver"가 아니라 "Validator"로 정한 이유: 5개 호출부 모두 검증된 엔티티 객체 자체를 재사용하지 않고 존재/소속 확인만 하기 때문이다.

**메서드 시그니처**
```java
package com.lightalm.service.support;

import com.lightalm.domain.TargetType;
import com.lightalm.exception.ResourceNotFoundException;
import com.lightalm.repository.IssueRepository;
import com.lightalm.repository.RequirementRepository;
import com.lightalm.repository.TestCaseRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;

@Component
@RequiredArgsConstructor
public class PolymorphicTargetValidator {

    private final RequirementRepository requirementRepository;
    private final IssueRepository issueRepository;
    private final TestCaseRepository testCaseRepository;

    /**
     * (targetType, targetId)로 식별되는 대상이 존재하고, projectId가 가리키는 프로젝트에
     * 속하는지 검증한다. 존재하지 않거나 다른 프로젝트 소속이면 ResourceNotFoundException(404).
     * 검증된 엔티티는 리턴하지 않는다(모든 호출부가 존재 확인 용도로만 쓰기 때문).
     */
    public void ensureExists(Long projectId, TargetType targetType, Long targetId) {
        switch (targetType) {
            case REQUIREMENT -> {
                var requirement = requirementRepository.findById(targetId)
                        .orElseThrow(() -> new ResourceNotFoundException("요구사항을 찾을 수 없습니다: " + targetId));
                if (!requirement.getProject().getId().equals(projectId)) {
                    throw new ResourceNotFoundException("요구사항을 찾을 수 없습니다: " + targetId);
                }
            }
            case ISSUE -> {
                var issue = issueRepository.findById(targetId)
                        .orElseThrow(() -> new ResourceNotFoundException("이슈를 찾을 수 없습니다: " + targetId));
                if (!issue.getProject().getId().equals(projectId)) {
                    throw new ResourceNotFoundException("이슈를 찾을 수 없습니다: " + targetId);
                }
            }
            case TEST_CASE -> {
                var testCase = testCaseRepository.findById(targetId)
                        .orElseThrow(() -> new ResourceNotFoundException("테스트케이스를 찾을 수 없습니다: " + targetId));
                if (!testCase.getProject().getId().equals(projectId)) {
                    throw new ResourceNotFoundException("테스트케이스를 찾을 수 없습니다: " + targetId);
                }
            }
            default -> throw new IllegalStateException("지원하지 않는 TargetType입니다: " + targetType);
        }
    }
}
```

`default` 분기를 명시적으로 `IllegalStateException`(500)으로 처리하는 이유: `TargetType`에 미래에 새 값이 추가됐을 때, 방어 코드가 없으면 조용히 `ISSUE`로 취급되며 데이터 무결성이 깨지는 기존 버그 패턴을 반복하게 된다. 새 값을 추가하는 개발자가 컴파일 타임(exhaustive switch 경고) 또는 최소한 런타임 예외로 이 클래스를 갱신해야 함을 명확히 알 수 있도록 한다.

### 예외 타입 통일 — 전부 404(`ResourceNotFoundException`)
"대상이 존재하지 않음"과 "대상은 존재하지만 다른 프로젝트 소속"을 구분하지 않고 모두 `ResourceNotFoundException`(404)으로 통일한다.

근거:
1. **다수결**: 기존 5곳 중 4곳(Comment/GitLink/Jenkins/Release)이 이미 이 방식이었다.
2. **보안/멀티테넌시 관점**: "다른 프로젝트 소속"인 경우를 400으로 응답하면, 요청자는 "이 ID가 (내 프로젝트는 아니지만) 어딘가에는 존재한다"는 사실을 알게 된다. 이는 크로스 테넌트 존재 노출(cross-tenant existence disclosure)이다. 404로 통일하면 "내 프로젝트 범위에서는 찾을 수 없음"으로 일관되게 응답해 이 정보 노출을 막는다. 이는 멀티테넌시 시스템에서 흔히 쓰이는 패턴과 일치한다.

### 적용 범위 — 5곳 전부 교체
`CommentService`, `GitLinkService`, `JenkinsBuildService`, `ReleaseService`, `TraceabilityService`의 기존 `verifyTargetExists`/`validateTargetExists`/`validateTarget` private 메서드를 모두 제거하고, `PolymorphicTargetValidator`를 주입받아 `ensureExists(projectId, targetType, targetId)` 호출로 대체한다.

### `TEST_CASE` 버그 수정
`PolymorphicTargetValidator`는 `REQUIREMENT`/`ISSUE`/`TEST_CASE` 3개 값을 모두 명시적으로 분기 처리한다(`testCaseRepository` 신규 주입). 이로써 `TraceabilityService.createLink()`가 `sourceType`/`targetType`으로 `TEST_CASE`를 받았을 때 더 이상 `issueRepository`로 잘못 조회하지 않고, 존재하면 정상 처리, 존재하지 않거나 다른 프로젝트 소속이면 "테스트케이스를 찾을 수 없습니다" 404를 정확히 반환한다.

주의: 이 ADR은 `TraceabilityService`가 `TEST_CASE`를 받아들이도록 "허용"하는 정책 결정을 내리는 것이 아니라, 이미 코드상 막혀 있지 않던 경로에서 발생하던 오조회 버그를 바로잡는 것이다. `TEST_CASE`를 추적성 링크의 유효한 대상으로 둘지 여부(정책)는 이 ADR의 범위 밖이며, 기존 동작(허용되어 있었지만 잘못 처리됨)을 "허용된 채로 올바르게 처리됨"으로 고치는 데 그친다.

## 결과 (Consequences)

### API 응답 코드 변경 (사전 고지 후 승인됨 — 유일한 하위 호환성 영향 지점)
`POST /api/projects/{projectId}/traceability-links`에서 `sourceType`/`targetType`이 가리키는 요구사항 또는 이슈가 **존재하지만 다른 프로젝트 소속인 경우**, 응답이 **400(Bad Request) → 404(Not Found)로 바뀐다.** 이 API를 호출하는 기존 클라이언트가 400 상태 코드에 의존한 별도 처리를 하고 있었다면 영향을 받을 수 있다. 프론트엔드 코드에서 이 케이스를 특별히 분기하는 로직이 없는지 developer가 구현 시 확인해야 한다.

이 외 4개 서비스(Comment/GitLink/Jenkins/Release)는 이미 404를 반환하고 있었으므로 응답 코드 변경이 없다.

### 장점
- 5곳에 흩어져 있던 사실상 동일한 코드가 `PolymorphicTargetValidator` 한 곳으로 모여 유지보수 포인트가 하나로 줄어든다.
- `TraceabilityService`의 `TEST_CASE` 오조회 버그가 해소된다.
- 예외 타입이 5곳 모두 일관되어, 이후 새로운 다형 연관 소비처를 추가할 때 참고할 단일 기준이 생긴다.
- 크로스 테넌트 존재 노출 리스크가 `TraceabilityService` 경로에서도 해소된다.

### 단점 / 리스크
- `TraceabilityService.createLink()`를 호출하는 기존 프론트/클라이언트가 400을 기대하고 있었다면 위 API 응답 코드 변경으로 깨질 수 있다(제품 오너 승인 완료, developer가 프론트 확인).
- `PolymorphicTargetValidator`가 `TestCaseRepository`까지 주입받으므로, 이 컴포넌트를 사용하는 모든 서비스가 간접적으로 `test_cases` 테이블 조회 경로를 갖게 된다. 순환 의존이나 레이어링 위반은 없음(모두 `repository` 계층 조회이며 `service.support` → `repository` 단방향 의존).
- 스키마/DB 변경은 없다(신규 마이그레이션 불필요) — 순수 애플리케이션 레벨 리팩터링이다.

### 하위 호환성 요약
| 서비스 | 기존 예외(다른 프로젝트 소속 케이스) | 변경 후 | 응답 코드 변경 여부 |
|---|---|---|---|
| CommentService | `ResourceNotFoundException`(404) | `ResourceNotFoundException`(404) | 없음 |
| GitLinkService | `ResourceNotFoundException`(404) | `ResourceNotFoundException`(404) | 없음 |
| JenkinsBuildService | `ResourceNotFoundException`(404) | `ResourceNotFoundException`(404) | 없음 |
| ReleaseService | `ResourceNotFoundException`(404) | `ResourceNotFoundException`(404) | 없음 |
| TraceabilityService | `ValidationException`(400) | `ResourceNotFoundException`(404) | **있음 (400→404)** |

### 구현 위임 범위 (developer)
1. `backend/src/main/java/com/lightalm/service/support/PolymorphicTargetValidator.java` 신규 작성 (위 시그니처 그대로)
2. `CommentService`, `GitLinkService`, `JenkinsBuildService`, `ReleaseService`, `TraceabilityService`에서 기존 private 검증 메서드 제거 후 `PolymorphicTargetValidator` 주입 및 호출로 교체
3. `PolymorphicTargetValidator`에 대한 단위 테스트 신규 작성(`PolymorphicTargetValidatorTest`) — REQUIREMENT/ISSUE/TEST_CASE 각각 존재/미존재/다른 프로젝트 소속 3가지 케이스 커버
4. `ReleaseServiceTest.addItem_rejectsTestCaseTargetType`는 `addItem()`의 사전 가드(TEST_CASE 자체를 거부)를 검증하는 테스트이므로 그대로 유지(회귀 없는지만 확인)
5. `TraceabilityService.createLink()`의 400→404 응답 코드 변경을 검증하는 테스트 추가(다른 프로젝트 소속 요구사항/이슈로 링크 생성 시도 시 404 확인)
6. 프론트엔드에서 추적성 링크 생성 실패를 400 코드로 특별 분기하는 곳이 있는지 확인(있다면 developer가 함께 수정)
