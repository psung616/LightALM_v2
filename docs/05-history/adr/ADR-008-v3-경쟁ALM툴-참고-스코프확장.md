# ADR-008: v3 확장 — 업계 ALM 툴의 일반적 기능 카테고리를 참고해 4개 영역 추가

## 맥락 (Context)
Phase 0~15(v1 MVP + v2 확장)가 완료된 뒤, 다음 확장을 검토하면서 업계에 널리 퍼진 상용 ALM 툴들에서 공통적으로 보이는 **일반적인 기능 카테고리**(다단계 검토, 특정 시점 스냅샷 비교, 위험 등록, 문서형 요구사항 열람, 대시보드 커스터마이징 등)를 참고하기로 했다.

`01-scope.md` §1.1은 "무거운 ALM 툴 없이" 핵심 기능만 관리하는 것을 프로젝트 철학으로 명시하고 있어, 이번 확장은 이 철학과 긴장 관계에 있다(아래 결과 참고). 또한 특정 상용 제품의 UI·문서·기능명을 그대로 옮기면 저작권 문제가 될 수 있어, 참고 범위와 원칙을 먼저 정해야 했다.

## 결정 (Decision)

### 저작권 준수 원칙 (`02-competitive-reference.md`에 상세)
1. 기능·개념만 참고한다(아이디어는 보호 대상이 아님). UI/문서 텍스트/로고/소스코드는 절대 복제하지 않는다.
2. 기능명은 프로젝트 고유 용어로만 서술하고, 특정 제품의 상표화된 기능명을 쓰지 않는다.
3. 어떤 문서에도 특정 제품명·회사명을 적지 않는다. 참고 배경은 "업계에서 흔히 쓰이는 상용 ALM 툴"처럼 일반화된 표현만 쓴다.
4. 디자인(색상/레이아웃/아이콘)은 참고하지 않고 이 프로젝트의 자체 디자인 시스템(`02-design/design-tokens/linear-style-tokens.md`) 하나로 통일한다.

### 추가하는 4개 영역 (Phase 16~19에 1:1 대응)
| 영역 | 우리 프로젝트 명칭 | 범위 | 설계 위치 |
|---|---|---|---|
| 다단계 검토/승인 | **리뷰 사이클(Review Cycle)** + **베이스라인(Baseline)** | 여러 검토자가 각자 승인/반려/의견만 남기는 방식(상태 전이 강제 아님, 기존 §1.2 DRAFT→APPROVED 게이트와는 별개) + 특정 시점 스냅샷 고정·비교 | 03-data-model.md §3.18~3.21 |
| 위험 식별/평가 | **위험 관리(Risk Register)** | 발생가능성×영향도 간이 점수화. 정식 FMEA 방법론 전체는 구현하지 않음 | 03-data-model.md §3.22 |
| 요구사항 문서형 열람 + 제품 라인별 재사용 | **요구사항 문서 뷰** + **변형 관리(Variant Management)** | 기존 상위/하위 계층(parent_requirement_id)을 문서 목차 형태로 재구성해 보여주는 읽기 중심 뷰(리치 텍스트 편집기 아님) + 요구사항에 변형 태그를 붙여 포함/제외/수정 여부 표시 | 03-data-model.md §3.23, 05-frontend.md §5.11 |
| 대시보드 커스터마이징 + 리포트 내보내기 | **대시보드 위젯 설정** + **리포트 내보내기** | 위젯 종류/배치 선택 + 추적성 매트릭스·테스트 실행 결과·감사 로그를 Excel/PDF로 내보내기 | 03-data-model.md §3.24, 04-api.md §4.21 |

API(§4.17~4.21), 화면(§5.11~5.15) 상세는 각 문서 참고. **이 ADR 시점에는 설계만 완료됐고 구현은 시작하지 않았다** — Phase 0~15까지만 완료 상태(CURRENT-STATE.md §1).

## 결과 (Consequences)
- **철학과의 긴장 관계**: 기능이 늘어날수록 "Light" 정체성에서 멀어질 위험이 있음을 인지하고, 각 영역을 업계 일반 개념의 최소 스코프로만 도입했다(정식 FMEA 전체·워드프로세서급 문서 편집기·상태 전이를 강제하는 리뷰 사이클 규칙은 명시적으로 제외 — `01-scope.md` §1.3, `02-competitive-reference.md` "참고하지 않은 것" 참고). 앞으로 추가 확장을 검토할 때도 "이게 정말 최소 스코프인가"를 매번 검증할 것을 권장한다.
- 장점: 기존 데이터 모델(요구사항/이슈/추적성/테스트케이스)을 재사용해 확장하므로 아키텍처 급변 없이 점진적으로 붙일 수 있음
- 단점: 리뷰 사이클·베이스라인·위험 관리·변형 관리 4개가 한 번에 늘어나 QA 검증 범위가 커짐 — Phase 16~19 착수 시 qa-tester 서브에이전트가 `09-quality-testing.md` 기준으로 각 영역 최소 커버리지를 별도 확인해야 함
- 이 ADR 자체가 한 번 유실됐다가 재작성된 이력이 있음(위 헤더 참고) — 향후 ADR을 작성하는 세션은 파일을 한글 파일명 포함 zip으로 전달할 때 인코딩 손실 위험을 인지할 것(README.md 참고)
