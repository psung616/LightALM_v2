# ADR-016: 세션 사용자 상태(활성 여부·시스템 역할)를 요청마다 DB로 재검증 + `User` 변경 컬럼만 UPDATE

## 맥락 (Context)

### 결함 1 [High] — 강등/비활성화된 사용자의 기존 세션이 권한을 유지하고 스스로 복권할 수 있음

qa-tester가 ADR-015 검증 중(2026-10-06) 로컬 docker-compose Postgres + 실제 API로 재현한 시나리오(원문 그대로 요약):

1. `qa15u3`(ADMIN) 로그인 상태 유지
2. `admin`이 `PUT /api/users/33 {systemRole:USER, enabled:false}` → `200`
3. `qa15u3`의 **기존 세션**으로 `PUT /api/users/33 {systemRole:ADMIN, enabled:true}` → `200` — **자기 복권**
4. 같은 세션으로 `POST /api/users {systemRole:ADMIN}` → `201` — **새 ADMIN 생성**

비활성화된 USER의 기존 세션도 계속 쓰기가 가능했다(요구사항 생성 `201`).

원인: 로그인 시 `UserPrincipal`(id/username/`systemRole`/`enabled` 등)이 `HttpSessionSecurityContextRepository`를 통해 세션의 `SecurityContext`에 저장되고, 이후 요청은 그 값을 그대로 쓴다. `@PreAuthorize("hasRole('ADMIN')")`는 세션에 고정된 authorities를, 서비스의 `principal.isAdmin()`(예: `ProjectMemberService.requireRole`)은 세션에 고정된 `systemRole`을 본다. 비활성화도 로그인 시점(`DaoAuthenticationProvider`의 `isEnabled()` 검사)에만 확인된다. ADR-015 "단점 / 리스크"에 "기존부터 있던 한계, 범위 밖"으로 적어 두었지만, 마지막 System Admin 보호(D3)와 ADMIN 전용 계정 생성(D2)을 무력화하므로 High로 반려됐다.

참고로 **프로젝트 역할**(`PROJECT_ADMIN`/`MEMBER`/`VIEWER`)은 `ProjectMemberService.findRole()`이 매 요청 `project_members`를 조회하므로 이 문제가 없다. 문제는 `users` 테이블의 `enabled`/`system_role` 두 값뿐이다.

### 결함 2 [Low] — `User` 엔티티 lost update로 활성 ADMIN 0명 가능성

`UserService.update()`는 email/fullName만 바꾸는 요청이면 행 락을 잡지 않는다(ADR-015 §3.1 — 활성 ADMIN 집합에서 빠지게 하는 요청만 락). 그런데 `User` 엔티티에 `@DynamicUpdate`/`@Version`이 없어 Hibernate가 **모든 컬럼**을 UPDATE한다. 그래서 "email만 수정" 트랜잭션이 엔티티를 읽은 뒤, 다른 트랜잭션이 같은 사용자의 `system_role`/`enabled`를 바꿔 커밋하면, email 트랜잭션의 UPDATE가 옛 `system_role`/`enabled`로 되돌린다. 예: (a) A가 X를 ADMIN으로 승격(커밋) → (b) Y 강등이 "X가 활성 ADMIN"이라 허용(커밋) → (c) (a) 이전에 X를 읽은 email 수정이 X를 USER로 되돌림 → 활성 ADMIN 0명.

## 결정 (Decision)

### D1. 요청마다 DB에서 사용자 상태를 재조회하는 필터를 추가한다 (`SessionPrincipalRefreshFilter`)

`com.lightalm.security.SessionPrincipalRefreshFilter`(`OncePerRequestFilter`)를 `SecurityFilterChain`에서 `AuthorizationFilter` **바로 앞**에 둔다(세션에서 `SecurityContext`가 복원되고 CSRF·로그인·로그아웃 필터를 지난 뒤, 인가 판단 전).

인증된 요청(`Authentication.getPrincipal()`이 `UserPrincipal`)마다 `UserRepository.findById(principal.id)`로 1회 PK 조회한 뒤:

| DB 상태 | 처리 |
|---|---|
| 행 없음 또는 `enabled=false` | `HttpSession.invalidate()` + `SecurityContextHolder.clearContext()` 후 **`401 UNAUTHORIZED`**(`JsonAuthenticationEntryPoint` 재사용, 기존 미인증 응답과 동일 본문). 체인을 더 진행하지 않는다 |
| `system_role`이 세션 값과 다름 | DB 값으로 새 `UserPrincipal`과 authorities를 만든 `UsernamePasswordAuthenticationToken.authenticated(...)`(기존 details 유지)로 `SecurityContext`를 교체하고 `HttpSessionSecurityContextRepository.saveContext()`로 **세션에도 저장**. 이어지는 `@PreAuthorize`/`principal.isAdmin()`/`@AuthenticationPrincipal`(`GET /api/auth/me` 포함)이 갱신된 값을 본다 |
| 같음 | 아무것도 바꾸지 않고 통과 |

익명 요청(`/api/auth/login`, `/api/public/theme`, `/api/webhooks/**`)과 `UserPrincipal`이 아닌 인증은 조회 없이 통과한다. email/fullName 등 다른 필드 변경은 재발급 조건이 아니다(범위 밖 — 권한과 무관).

### D2. 대안 비교 — SessionRegistry로 해당 사용자 세션 만료는 채택하지 않음

| 기준 | D1 요청마다 재조회(채택) | 대안: 사용자 변경 시 `SessionRegistry`로 세션 만료 |
|---|---|---|
| 반영 시점 | 다음 요청부터 즉시 | 즉시(등록된 세션에 한해) |
| 커버리지 | API·DB 직접 수정(`psql`, 10-deployment.md 부록 F 복구 SQL 포함) 모두 | `UserService`를 거친 변경만. DB 직접 수정은 놓침 |
| 배포 시점 기존 세션 | 바로 적용(세션에 이미 있는 `UserPrincipal.id`만 필요) | 배포 전 로그인한 세션은 레지스트리에 없어 만료 불가 |
| 구현 변경량 | 필터 1개 + `SecurityConfig` 1줄 | `SessionRegistry` 빈, `HttpSessionEventPublisher`, 커스텀 JSON 로그인 필터에 `SessionAuthenticationStrategy` 수동 연결, `UserService` 두 메서드에 만료 호출 |
| 역할 변경 시 UX | 세션 유지, 권한만 갱신 | 강제 로그아웃 |
| 비용 | 인증된 요청마다 PK SELECT 1회(`users` 소규모 테이블, 인덱스 조회) | 변경 시에만 비용 |
| 다중 인스턴스 | 상태 없음, 그대로 동작 | 인메모리 레지스트리는 인스턴스 간 공유 안 됨 |

D1이 더 단순하고 확실하다(누락 경로가 없음). PK 조회 1회 비용은 이 시스템 규모(사내 단일 인스턴스)에서 무시 가능하다고 판단했다.

### D3. `User` 엔티티에 `@DynamicUpdate` (결함 2)

`com.lightalm.domain.User`에 Hibernate `@DynamicUpdate`를 붙여, flush 시 **실제로 값이 바뀐(dirty) 컬럼만** UPDATE한다. email/fullName만 바꾸는 요청은 `email`/`full_name`/`updated_at`만 쓰므로 동시 커밋된 `system_role`/`enabled`를 되돌리지 않는다. `UserService.update()`가 요청의 `systemRole`/`enabled`를 엔티티에 다시 set 하더라도, 읽은 값과 같으면 dirty가 아니라 UPDATE에 포함되지 않는다.

- 불변식 영향: 활성 ADMIN 집합에서 **빠지게** 하는 쓰기(ADMIN 해제·비활성화)는 여전히 ADR-015 §3.4의 `PESSIMISTIC_WRITE` 락 경로를 탄다. `@DynamicUpdate` 이후 락 없이 실행되는 쓰기는 `system_role`/`enabled`를 건드리지 않거나 활성 ADMIN을 **늘리는** 방향(승격·재활성화)뿐이라 0명으로 만들 수 없다.
- 대안 `@Version`(낙관적 락)은 `users`에 `version` 컬럼이 필요해 새 마이그레이션이 필요하고(공용 DB 스키마 변경), 충돌 시 409 처리 경로를 새로 만들어야 한다. "update 경로에서 항상 대상 행 잠금"은 동작하지만 모든 프로필 수정이 락을 잡게 된다. 스키마 변경 없이 한 줄로 해결되는 `@DynamicUpdate`를 택했다.

### D4. 스키마 변경 없음

마이그레이션을 추가하지 않는다(V18 최신 유지).

## 결과 (Consequences)

### 장점
- ADMIN 해제 즉시 그 사용자의 기존 세션에서 `@PreAuthorize("hasRole('ADMIN')")` API가 403, 비활성화·삭제 즉시 모든 인증 API가 401(세션 폐기) — 자기 복권·ADMIN 생성 경로 차단
- DB 직접 수정(복구 SQL 등)도 다음 요청에 반영
- 마지막 활성 ADMIN 불변식이 email/fullName 동시 수정으로 깨지지 않음

### 단점 / 리스크
- 인증된 모든 요청에 `users` PK SELECT 1회가 추가된다(커넥션 풀 사용 1회 추가). 현재 규모에서 비차단
- 이미 처리 중인 요청(필터 통과 후 서비스 실행 중)에는 반영되지 않는다 — 다음 요청부터 반영
- 비밀번호 변경은 이 필터의 재검증 대상이 아니다(다른 세션을 끊지 않음) — 기존 동작 유지, 범위 밖
- `@DynamicUpdate`는 `User` 엔티티에만 적용(다른 엔티티는 기존과 동일)
