# ADR-011: 회원가입(Self-Signup) 페이지 + 라이센스 파일 관리 서브시스템 — 스코프 확장 제안

## 맥락 (Context)

제품 오너로부터 다음 두 기능에 대한 요청이 들어왔다.

1. 사용자가 관리자 개입 없이 직접 계정을 만들 수 있는 **회원가입 페이지**. 요청에 명시된 입력 항목은 **ID(username), EMAIL, 이름(fullName)** 세 가지뿐이었다.
2. 업계 상용 ALM 툴(예: 다단계 검토/시트 기반 라이센싱을 쓰는 제품들)이 흔히 쓰는 방식처럼, **라이센스 파일을 업로드 → 파싱 → 저장하고, 그 안에 명시된 시트(seat) 수/만료일/라이센스 타입에 따라 신규 가입·로그인을 제어**하는 서브시스템.

### 현재 상태 (CURRENT-STATE.md §1, 03-process/06-auth.md 확인)
- `users` 테이블(`V1__init.sql`)에는 이미 `username(50,UNIQUE)`, `password(255, NOT NULL, BCrypt)`, `email(120,UNIQUE)`, `full_name(100)`, `system_role`, `enabled` 컬럼이 존재한다.
- 자체 폼 로그인(Spring Security 세션 기반, `BCryptPasswordEncoder`)만 지원하고(`01-scope.md` §1.3 "SSO/OAuth 로그인 제외"), **self-signup은 전혀 없다** — 계정은 오직 시스템 `ADMIN`이 `POST /api/users`(`CreateUserRequest{username,password,email,fullName,systemRole}`)로만 생성한다.
- 라이센스 개념은 코드/데이터 모델 어디에도 없다.

### 비밀번호 필드에 대한 판단
요청에는 ID/EMAIL/이름만 명시됐지만, `users.password`는 `NOT NULL`이고 로그인 수단이 자체 폼 로그인 하나뿐이므로 비밀번호 없이는 가입한 계정으로 로그인할 방법이 없다. 이는 제품 오너가 "로그인 수단"을 설명하는 과정에서 당연히 필요한 항목을 누락했을 가능성이 높다고 판단해, **이 ADR은 비밀번호(및 프론트 전용 비밀번호 확인) 입력 필드를 포함한다.** 이 필드는 사용자의 원 요청에는 없었고, 로그인에 필수이기 때문에 architect 판단으로 추가한 것임을 명확히 기록한다.

### 스코프 확장 여부 판단
`01-scope.md` §1.2(핵심 스코프)에는 self-signup도 라이센스 관리도 없다. §1.3(명시적 비스코프)에도 두 기능을 금지하는 항목은 없다. 즉 **금지된 기능은 아니지만 핵심 스코프에도 없는 완전히 새로운 기능**이며, ADR-008(v3 확장)과 동일한 패턴의 **스코프 확장 제안**이다. ADR-008 선례를 따라 이 ADR은 설계만 확정하고, 구현·`01-scope.md` 반영은 제품 오너 승인 이후 별도 단계로 미룬다.

이 확장과 직접 충돌하는 기존 비스코프 2건을 미리 짚어둔다.
- **§1.3 "알림/이메일 발송 제외"** → 이 설계는 이메일 인증 발송 단계를 포함하지 않는다(가입 즉시 `enabled=true`로 계정이 활성화된다). 이메일 인증까지 필요하다면 별도 ADR + 스코프 승인이 필요하다.
- **§1.3 "파일 첨부 기능 제외"** → 라이센스 파일 업로드는 범용 첨부파일 기능의 재도입이 아니다. 업로드 대상은 **관리자가 올리는 단일 시스템 설정 파일**(수십 바이트~수 KB의 텍스트) 하나뿐이고, 저장도 파일시스템이 아니라 DB `TEXT` 컬럼에 원문을 그대로 넣는 것으로 한정한다. 요구사항/이슈에 파일을 첨부하는 일반 기능과는 범위와 목적이 다르다는 점을 분명히 구분한다.

### 저작권/참고 원칙
ADR-008의 저작권 준수 원칙을 그대로 적용한다. 라이센스 파일의 정확한 포맷(필드명, 바이너리 구조, 서명 알고리즘 조합 등)은 업계의 특정 제품을 그대로 베끼지 않고, "라이센스 파일 업로드 → 파싱 → 시트/만료 제약 적용"이라는 **개념**만 참고해 이 프로젝트 자체의 포맷("Light ALM 라이센스 디스크립터")을 새로 정의한다.

## 결정 (Decision)

> 이 ADR은 아직 `01-scope.md`에 반영되지 않은 신규 기능의 설계를 **ADR 본문 안에 자기완결적으로** 담는다. `03-data-model.md`/`04-api.md`/`05-frontend.md`의 해당 절은 제품 오너 승인 이후 별도 작업으로 반영한다(아래 "다음 단계" 참고).

### 1. 회원가입 페이지

#### 1.1 화면
- 새 라우트 `/signup`. 기존 `/login`과 동일하게 **비인증 전용**(`GuestOnlyRoute`로 감싸, 로그인 상태에서는 접근 시 `/`로 리다이렉트). `/login` 화면에 "계정이 없으신가요? 회원가입" 링크를 추가하고, `/signup`에도 "이미 계정이 있으신가요? 로그인" 링크를 둔다.
- 입력 필드:

| 필드 | 요청 출처 | 비고 |
|---|---|---|
| username (ID) | 제품 오너 요청 | |
| email | 제품 오너 요청 | |
| fullName (이름) | 제품 오너 요청 | |
| password | **architect 추가** — 요청에는 없었으나 로그인에 필수라 포함함 | |
| passwordConfirm | **architect 추가** — 프론트엔드 전용 입력이지만 백엔드에도 전송해 재검증(방어적 이중 검증) | DB 컬럼 없음, `users`에 저장 안 함 |

- 제출 성공 시 **자동 로그인은 하지 않는다.** "가입이 완료되었습니다. 로그인해주세요" 메시지와 함께 `/login`으로 이동시킨다. 근거: 현재 인증 진입점이 `JsonUsernamePasswordAuthenticationFilter`(`/api/auth/login`) 하나뿐이라, 가입 응답에서 세션을 바로 발급하려면 이 필터와 별개로 `SecurityContext`를 수동 구성하는 코드가 추가로 필요해진다. "Light" 철학(불필요한 복잡도 최소화) 하에서는 가입 후 한 번 더 로그인하게 하는 쪽이 기존 인증 흐름을 전혀 건드리지 않는 더 단순한 선택이다.

#### 1.2 API
`POST /api/auth/signup` — **공개**(`permitAll`, 기존 `/api/auth/login`과 동일한 예외 경로에 추가)

요청 본문:
```json
{
  "username": "jdoe",
  "email": "jdoe@example.com",
  "fullName": "John Doe",
  "password": "P@ssw0rd123",
  "passwordConfirm": "P@ssw0rd123"
}
```

검증 규칙(기존 `CreateUserRequest`의 제약과 동일하게 맞춰 비일관성을 만들지 않는다):

| 필드 | 규칙 |
|---|---|
| username | `@NotBlank`, `@Size(max=50)` |
| email | `@NotBlank`, `@Email`, `@Size(max=120)` |
| fullName | `@NotBlank`, `@Size(max=100)` |
| password | `@NotBlank`, `@Size(min=8, max=100)` |
| passwordConfirm | `@NotBlank`; 서비스 레이어에서 `password.equals(passwordConfirm)` 확인, 불일치 시 `400 VALIDATION_ERROR` "password와 passwordConfirm이 일치하지 않습니다." |

서버 측 강제 사항(요청 바디에 실려 와도 무시):
- `systemRole`은 **항상 `USER`로 고정**한다. 가입 요청 DTO 자체에 `systemRole` 필드를 두지 않아 권한 상승 경로를 원천 차단한다(기존 `POST /api/users`의 ADMIN 전용 생성 경로와 분리).
- `enabled`은 **항상 `true`**로 즉시 활성화한다(이메일 인증 없음 — 위 §1.3 비스코프 검토 참고).
- 가입한 사용자는 어떤 프로젝트에도 자동으로 속하지 않는다. 프로젝트 멤버 추가는 기존처럼 `PROJECT_ADMIN`이 `POST /api/projects/{id}/members`로 수행한다(기존 흐름 변경 없음).

라이센스 연동(§2에서 상세): 가입 요청은 사용자 생성 직전에 `LicenseEnforcementService.requireActiveLicense()`와 `requireSeatAvailable()`를 통과해야 한다. 실패 시:

| 상황 | HTTP | error 코드 |
|---|---|---|
| 활성 라이센스 없음/만료 | 403 | `LICENSE_INVALID` |
| 시트 한도 초과(`enabled=true`인 사용자 수 ≥ `seat_limit`) | 403 | `LICENSE_SEAT_LIMIT_EXCEEDED` |

성공 응답: `201 Created`, 기존 `UserResponse`를 재사용(새 DTO를 만들지 않음).

#### 1.3 가입 스팸/중복 가입에 대한 설계상 한계 (명시적으로 인지하고 넘어가는 리스크)
- 중복 가입 방지는 기존 `users.username`/`users.email` UNIQUE 제약만으로 처리한다(동일 이메일/ID 재가입은 DB 제약으로 거부되고 `409` 또는 기존 예외 처리 패턴을 따른다).
- CAPTCHA, 이메일 인증, 가입 레이트리밋은 **포함하지 않는다** — 이메일 발송이 비스코프(§1.3)이기 때문이며, 레이트리밋은 이번 요청 범위를 벗어난다. 스팸 가입이 실제로 문제가 되면 관리자가 기존 `DELETE /api/users/{id}`(soft-disable)로 대응하거나, 라이센스 시트 한도 자체가 자연스러운 상한선 역할을 한다. 더 강한 방지책이 필요해지면 별도 ADR로 다룬다.

### 2. 라이센스 관리 서브시스템

#### 2.1 개념 (참고는 개념 수준으로 한정 — 특정 제품명/포맷 비복제)
"라이센스 파일을 관리자가 업로드하면 시스템이 파싱해서 저장하고, 그 안의 시트 수/만료일/타입에 따라 신규 가입·로그인을 제한한다"는 **개념**만 가져온다. 이 프로젝트 자체 포맷을 다음과 같이 새로 정의한다(가칭 "Light ALM 라이센스 디스크립터").

#### 2.2 파일 포맷 (자체 정의)
UTF-8 JSON 텍스트 파일(확장자 자유, 권장 `.json`):

```json
{
  "licenseKey": "LALM-LIC-2026-0001",
  "organizationName": "ACME Corp",
  "licenseType": "STANDARD",
  "seatLimit": 50,
  "issuedAt": "2026-01-01T00:00:00Z",
  "expiresAt": "2027-01-01T00:00:00Z",
  "signature": "base64(HMAC-SHA256)"
}
```

- `licenseType`: `TRIAL` / `STANDARD` / `ENTERPRISE` — 이번 설계에서는 **메타데이터로만 저장**하고 기능 차등 적용(feature gating)은 하지 않는다(과설계 방지). 추후 특정 타입에 따라 기능을 제한하려면 별도 ADR이 필요하다.
- `expiresAt`은 `null` 허용(무기한 라이센스).
- `signature` = `licenseKey|organizationName|licenseType|seatLimit|issuedAt|expiresAt`를 `\n`으로 join한 canonical 문자열에 대해 `HMAC-SHA256(secret, canonical)`을 계산한 뒤 Base64 인코딩한 값. `secret`은 백엔드 환경변수 `LICENSE_SIGNING_SECRET`(ADR-001의 `${VAR:default}` 오버라이드 패턴을 그대로 따름)에 보관하고, 라이센스 파일을 발급하는 쪽(관리자/운영 담당)도 동일한 secret으로 서명을 생성해야 한다.
- **의도적 설계 한계**: 비대칭키(RSA 서명 등)가 아니라 대칭키(HMAC)를 쓴다. 이 시스템은 다수 고객사에 배포되는 상용 제품이 아니라 **단일 조직이 자체 서버에 배포해 운영하는 내부 도구**(CURRENT-STATE.md §3 "사내 공용 Postgres"와 동일한 전제)이므로, 위협 모델이 "정교한 공격자의 우회 방지"가 아니라 "관리 UI를 거치지 않은 임의 수정 방지(실수/캐주얼 변조 방지) + 시트/만료 관리"다. 서버 환경변수를 읽을 수 있는 사람은 유효한 라이센스 파일을 직접 만들 수 있다는 점을 운영 주체가 인지해야 한다 — 강한 DRM이 아니다. 이 한계는 아래 "결과" 섹션에도 리스크로 다시 기록한다. (실제 구현 시 이 canonical 문자열 처리에서 생긴 세부 차이는 §"실제 구현과 설계의 차이" 참고.)

#### 2.3 업로드 → 파싱 → 저장 → 적용 흐름
1. 관리자가 `/admin/licenses` 화면에서 파일을 선택해 업로드.
2. `POST /api/admin/licenses` (multipart, `file` 파트) — **ADMIN 전용**.
3. `LicenseFileParser`가 raw 텍스트를 읽어 JSON으로 파싱(크기 상한 16KB — 그 이상은 `400 LICENSE_FILE_TOO_LARGE`).
4. `LicenseSignatureVerifier`가 canonical 문자열로 HMAC을 재계산해 `signature`와 비교(상수 시간 비교). 불일치 시 저장하지 않고 `400 LICENSE_SIGNATURE_INVALID` 반환.
5. 추가 검증: `seatLimit > 0`, `expiresAt`이 있다면 업로드 시점 이후여야 함(이미 만료된 파일을 신규 등록하는 것은 의미가 없으므로 `400 LICENSE_ALREADY_EXPIRED`로 거부).
6. `LicenseCommandService.apply(...)`가 하나의 트랜잭션 안에서: 기존 `status='ACTIVE'` 행을 `SUPERSEDED`로 변경 → 새 행을 `ACTIVE`로 삽입 → `audit_logs`에 `CREATE`/`LICENSE` 기록(§3.2 참고).
7. 응답: 저장된 라이센스 상세 + 현재 시트 사용량(`seatsUsed`, `seatsRemaining`).

> 실제 메서드명은 `LicenseCommandService.upload(MultipartFile, UserPrincipal)`이다(설계 당시 가칭 `apply(...)`보다 "업로드 요청을 받아 전체 흐름을 수행한다"는 의미를 분명히 드러내는 이름으로 확정). 그 외 실제 구현에서 생긴 차이는 §"실제 구현과 설계의 차이" 참고.

적용(enforcement)은 **두 개의 독립된 게이트**로 나눈다 — 하나로 합치면 "기존 계정이 로그인하다가 시트가 줄어서 갑자기 잠긴다"는 부작용이 생기므로 명확히 분리한다.

| 게이트 | 조건 | 적용 대상 | ADMIN 예외 |
|---|---|---|---|
| A. 라이센스 유효성 게이트 | 활성(`ACTIVE`) 라이센스가 없음 또는 `expires_at` < now() | ① 모든 비-ADMIN 로그인 ② 모든 신규 계정 생성(가입 + 관리자의 `POST /api/users`) | 로그인(①)은 시스템 `ADMIN`은 항상 통과 — 라이센스가 없어도 관리자가 로그인해서 새 라이센스를 올릴 수 있어야 하는 복구 경로이기 때문. 신규 계정 생성(②)은 ADMIN이 생성하는 경우도 동일하게 막는다(라이센스 없이 계정을 무한정 만들 수 있으면 게이트 자체가 무력화되므로) |
| B. 시트 한도 게이트 | `enabled=true`인 `users` 행 수 ≥ 활성 라이센스의 `seat_limit` | 신규 계정 생성(가입 + 관리자 생성)만 | 없음 — 관리자도 시트 초과분은 만들 수 없다. 단, 기존 로그인은 전혀 영향받지 않는다(이미 만들어진 계정은 라이센스를 교체해도 계속 로그인 가능) |

이 분리 덕분에 "관리자가 라이센스를 20시트짜리로 교체했는데 이미 25명이 쓰고 있던 경우" 같은 상황에서도 **기존 25명은 계속 로그인 가능**하고, **26번째 신규 계정만 막힌다** — 운영 중 갑작스러운 서비스 중단을 피하는 의도적 설계다.

#### 2.4 API
| Method | Path | 설명 | 권한 |
|---|---|---|---|
| POST | `/api/admin/licenses` | 라이센스 파일 업로드(multipart) → 파싱/검증/적용 | ADMIN |
| GET | `/api/admin/licenses/current` | 현재 활성 라이센스 상세 + 시트 사용량 | ADMIN |
| GET | `/api/admin/licenses` | 라이센스 업로드 이력(페이지네이션) | ADMIN |
| GET | `/api/public/license-status` | `{signupAllowed: boolean, reason: string\|null}` — 시트/라이센스 번호 등 민감 정보는 내려주지 않음 | 공개 |

`GET /api/public/license-status`는 `/signup` 화면이 폼을 보여주기 전에 "현재 가입이 비활성화되어 있습니다" 같은 안내를 미리 띄우기 위한 용도로, 응답을 최소 정보로 제한해 라이센스 세부 정보가 비인증 상태로 노출되지 않게 한다.

> 게이트 A/B의 예외는 각각 `com.lightalm.license.domain.LicenseInvalidException`(403 `LICENSE_INVALID`)과 `LicenseSeatLimitExceededException`(403 `LICENSE_SEAT_LIMIT_EXCEEDED`)으로 구현했고, 업로드 거부(400 계열)는 `LicenseFileRejectedException`(에러코드를 필드로 보유) 하나로 통합했다. 추가된 `LICENSE_FILE_INVALID` 코드 등 자세한 내용은 §"실제 구현과 설계의 차이" 참고.

#### 2.5 화면
- `/admin/licenses` — ADMIN 전용. 현재 라이센스 상태(조직명/타입/시트 사용량 `seatsUsed / seatLimit`/만료일, D-day 표시) + 업로드 이력 테이블 + 새 파일 업로드 버튼.
- `TopNavbar`의 "사용자 관리"(`/admin/users`) 옆에 "라이센스 관리" 링크를 ADMIN에게만 조건부 노출(기존 `/admin/users` 노출 패턴과 동일).

### 3. DB 스키마

#### 3.1 신규 테이블 `licenses`
| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGSERIAL | PK |
| license_key | VARCHAR(100) | UNIQUE, NOT NULL |
| organization_name | VARCHAR(150) | NOT NULL |
| license_type | VARCHAR(20) | NOT NULL, CHECK IN ('TRIAL','STANDARD','ENTERPRISE') |
| seat_limit | INTEGER | NOT NULL, CHECK (seat_limit > 0) |
| issued_at | TIMESTAMP | NOT NULL |
| expires_at | TIMESTAMP | NULL 허용(무기한) |
| status | VARCHAR(20) | NOT NULL, CHECK IN ('ACTIVE','SUPERSEDED','REVOKED'), DEFAULT 'ACTIVE' |
| raw_file_name | VARCHAR(255) | NOT NULL (업로드 원본 파일명, 감사용) |
| raw_payload | TEXT | NOT NULL (업로드된 파일 원문 전체 — 재검증/감사용. 일반 첨부파일 저장소가 아니라 이 설정 파일 하나만을 위한 컬럼) |
| signature_valid | BOOLEAN | NOT NULL DEFAULT true (파싱 시점 서명 검증 결과 기록. 검증 실패 건은 저장하지 않으므로 사실상 항상 true — 감사 추적용 플래그) |
| uploaded_by | BIGINT | FK → users.id, ON DELETE SET NULL |
| uploaded_at | TIMESTAMP | NOT NULL DEFAULT now() |

`ACTIVE` 상태는 항상 최대 1건만 존재해야 하므로 부분 유니크 인덱스로 DB 레벨에서 강제한다.
```sql
CREATE UNIQUE INDEX uq_licenses_single_active ON licenses(status) WHERE status = 'ACTIVE';
```

#### 3.2 기존 테이블 변경
- **`users`: 변경 없음.** username/email/full_name/password/enabled/system_role이 이미 존재하므로 회원가입 기능 자체는 새 컬럼이 필요 없다.
- **`audit_logs.target_type` CHECK 제약에 `'LICENSE'` 추가**(선택적이지만 §2.3 7단계의 감사 기록을 위해 필요). 기존 패턴(`V3__test_cases.sql`이 `traceability_links`/`comments` CHECK를 갱신한 방식)과 동일하게 `DROP CONSTRAINT IF EXISTS` 후 재생성한다.

#### 3.3 마이그레이션 제안 (참고용 SQL — 실제 파일은 생성하지 않음, developer가 구현 시점에 생성)
기존 V1~V8은 수정하지 않는다. 아래 번호는 **이 설계 작성 시점(V8까지 존재) 기준 제안**이며, 실제 구현 착수 시점에 다른 기능(예: v3 Phase16~19)이 먼저 V9/V10을 선점했다면 developer가 그 다음 번호로 밀어서 배정한다 — 이 ADR은 번호 자체를 확정하지 않는다.

```sql
-- (제안) V9__create_license_tables.sql
CREATE TABLE IF NOT EXISTS licenses (
    id BIGSERIAL PRIMARY KEY,
    license_key VARCHAR(100) NOT NULL UNIQUE,
    organization_name VARCHAR(150) NOT NULL,
    license_type VARCHAR(20) NOT NULL CHECK (license_type IN ('TRIAL','STANDARD','ENTERPRISE')),
    seat_limit INTEGER NOT NULL CHECK (seat_limit > 0),
    issued_at TIMESTAMP NOT NULL,
    expires_at TIMESTAMP NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE','SUPERSEDED','REVOKED')),
    raw_file_name VARCHAR(255) NOT NULL,
    raw_payload TEXT NOT NULL,
    signature_valid BOOLEAN NOT NULL DEFAULT true,
    uploaded_by BIGINT REFERENCES users(id) ON DELETE SET NULL,
    uploaded_at TIMESTAMP NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX IF NOT EXISTS uq_licenses_single_active ON licenses(status) WHERE status = 'ACTIVE';
```

```sql
-- (제안) V10__add_license_to_audit_target_type.sql
ALTER TABLE audit_logs DROP CONSTRAINT IF EXISTS chk_audit_logs_target_type;
ALTER TABLE audit_logs ADD CONSTRAINT chk_audit_logs_target_type
    CHECK (target_type IN ('REQUIREMENT','ISSUE','TEST_CASE','RELEASE','PROJECT','USER','TRACEABILITY_LINK','LICENSE'));
```

두 파일 모두 `ADD COLUMN IF NOT EXISTS`류는 아니지만, `CREATE TABLE IF NOT EXISTS`/`CREATE UNIQUE INDEX IF NOT EXISTS`/`DROP CONSTRAINT IF EXISTS` 조합으로 **재실행해도 오류가 나지 않는 idempotent 형태**를 유지했다(ADR-002/006 원칙).

### 4. 코드 구조 — 신규 기능 패키지 배치

이 두 기능은 Phase 0~15 레거시 코드가 아니라 **완전히 새로운 기능**이므로, `docs/CLAUDE.md`의 "새 파일은 기능별 패키지에 만든다" 원칙과 `11-structure-migration-plan.md` §5의 "2단계: v3 신규 기능을 새 구조로 먼저 적용" 선례를 그대로 따른다(v3 Phase16~19보다 이 기능이 먼저 구현되더라도 같은 원칙 적용).

```
com.lightalm.auth/              (신규)
├── api/      SelfSignupController (POST /api/auth/signup)
├── dto/      SignupRequest, (응답은 기존 UserResponse 재사용)
└── service/  SelfSignupService (검증 → LicenseEnforcementService 호출 → UserRepository.save)

com.lightalm.license/           (신규)
├── domain/   License(@Setter 금지, supersede()/revoke() 같은 도메인 동사 메서드로 상태 변경), LicenseType, LicenseStatus
├── repository/ LicenseRepository
├── api/      LicenseAdminController(업로드/조회/이력), PublicLicenseStatusController
├── dto/      LicenseUploadResponse, LicenseSummaryResponse, LicenseDetailResponse, PublicLicenseStatusResponse
└── service/  LicenseFileParser, LicenseSignatureVerifier, LicenseCommandService, LicenseQueryService, LicenseEnforcementService
```

`LicenseEnforcementService`는 GLOSSARY.md §5의 동사 규칙(검증·실패 시 예외는 `require`)을 따라 `requireActiveLicense()`, `requireSeatAvailable()` 메서드명을 쓴다(`ProjectMemberService.requireRole(...)`과 동일한 네이밍 패턴).

#### 4.1 불가피하게 건드려야 하는 기존(레거시) 파일
새 파일을 추가하는 것이 아니라 기존 파일에 최소한의 훅만 추가한다.

| 파일 | 변경 내용 |
|---|---|
| `com.lightalm.config.SecurityConfig` | `permitAll()` 목록에 `/api/auth/signup`, `/api/public/license-status` 추가 |
| `com.lightalm.security.JsonAuthenticationSuccessHandler` | 로그인 성공 처리 직전/직후에 `LicenseEnforcementService.requireActiveLicense(principal)` 호출 — ADMIN이면 통과, 아니면 실패 시 세션 무효화 후 `403 LICENSE_INVALID` 반환(§2.3 게이트 A) |
| `com.lightalm.service.UserService` (관리자의 `POST /api/users` 처리부) | 사용자 생성 직전에 `LicenseEnforcementService.requireActiveLicense()` + `requireSeatAvailable()` 호출(§2.3 게이트 A·B, ADMIN 생성 경로도 동일 적용) |

왜 `UserDetails.isAccountNonExpired()` 같은 Spring Security 표준 플래그를 재활용하지 않았는지: 그 플래그는 "이 계정 자체의 상태"를 뜻하는 것이고, 라이센스는 "시스템 전역 상태"이기 때문에 의미가 다르다. 계정별 플래그에 전역 상태를 끼워 넣으면 이후 코드를 읽는 사람이 "이 계정이 왜 만료됐지?"로 혼동한다. 그래서 `AuthenticationSuccessHandler` 레벨에서 별도로 체크하는 쪽을 택했다.

### 5. `06-auth.md` 기존 설계와의 정합성

- 세션 기반 인증(Spring Security `SecurityFilterChain`, `JSESSIONID`)과 `BCryptPasswordEncoder`는 **그대로 재사용**한다. 회원가입도 기존 `PasswordEncoder` 빈으로 해싱하며 새 인코더를 추가하지 않는다.
- `UserDetailsService` 구현체(`CustomUserDetailsService`)는 **변경하지 않는다** — 라이센스 체크는 위 §4.1처럼 `AuthenticationSuccessHandler` 레벨에서 수행하므로 인증 자체의 흐름(자격증명 검증)과는 분리된다.
- 프로젝트 단위 권한 검사(`ProjectMemberService.requireRole`)와는 전혀 다른 축(시스템 전역 vs 프로젝트별)이므로 기존 메서드를 확장하지 않고 `LicenseEnforcementService`를 새로 둔다 — 그러나 네이밍 동사(`require`)는 동일하게 맞춘다.
- `CORS`/`CSRF` 설정은 변경 없음. `POST /api/admin/licenses`가 multipart이므로 프론트가 `Content-Type: multipart/form-data`로 보낼 때도 기존 CSRF 쿠키(`XSRF-TOKEN` → `X-XSRF-TOKEN` 헤더) 전송 방식은 동일하게 적용된다(웹훅처럼 CSRF 예외를 추가할 필요 없음 — 관리자가 브라우저로 직접 올리는 폼이기 때문).

## 결과 (Consequences)

### 장점
- 관리자가 매번 직접 계정을 만들지 않아도 되어 온보딩 마찰이 줄어든다.
- 라이센스 서브시스템이 기존 `users` 테이블을 재사용하고 새 테이블(`licenses`) 하나만 추가하므로 구조 변경이 작다.
- 두 게이트(유효성/시트)를 분리해, 라이센스 교체 시 기존 사용자가 갑자기 로그인이 막히는 사고를 설계적으로 방지했다.
- Polarion 등 특정 제품의 실제 포맷을 복제하지 않고 이 프로젝트 전용의 단순한 JSON+HMAC 포맷을 새로 정의해 저작권 리스크를 피했다.

### 단점 / 리스크
- **서명 키 노출 리스크**: HMAC 대칭키(`LICENSE_SIGNING_SECRET`) 방식이라, 서버 환경변수에 접근 가능한 사람은 유효한 라이센스 파일을 직접 만들 수 있다. 이는 강한 DRM이 아니라 "관리 UI를 거치지 않은 캐주얼한 변조 방지 + 시트/만료 운영 관리" 수준의 보증이라는 점을 운영 문서(`10-deployment.md` 또는 `CURRENT-STATE.md §6` 알려진 리스크 목록)에 추가로 기록해야 한다.
- **가입 스팸/중복 가입 방지 미흡**: 이메일 인증·CAPTCHA·레이트리밋이 없다(§1.3 이메일 비스코프 때문). DB UNIQUE 제약과 시트 한도만으로 방어한다 — 실사용 중 문제가 되면 별도 ADR이 필요하다.
- **ADMIN 로그인 예외의 부트스트랩 전제**: 라이센스가 없거나 만료돼도 시스템 `ADMIN`은 항상 로그인할 수 있게 설계했는데, 이는 "최소 1개의 활성 ADMIN 계정이 항상 존재한다"는 전제에 의존한다. 모든 ADMIN 계정이 비활성화(`enabled=false`)된 상태에서 라이센스까지 만료되면 아무도 새 라이센스를 올릴 수 없는 복구 불가 상태가 된다 — 운영 가이드에 "ADMIN 계정 최소 1개 유지" 권고를 추가해야 한다.
- **기존 동작 변경(하위 호환성 영향)**: 현재 `POST /api/users`(관리자의 사용자 생성)는 라이센스 개념 없이 무제한으로 계정을 만들 수 있다. 이 설계가 구현되면 **관리자조차 유효한 라이센스 없이는 신규 계정을 만들 수 없게 된다** — 기존 API 계약이 바뀌는 지점이므로 구현 시 developer는 이 엔드포인트의 기존 테스트가 "라이센스 없음" 상태를 가정하고 있다면 함께 수정해야 한다. 운영 전환 시에는 **구현 배포 전에 최소 1건의 유효한 라이센스를 먼저 업로드해둬야** 기존 관리자 워크플로우가 끊기지 않는다.
- `licenseType`을 메타데이터로만 저장하고 기능 차등 적용을 하지 않기로 했으므로, 향후 "ENTERPRISE만 v3 기능 사용 가능" 같은 요구가 생기면 이 ADR의 결정을 다시 열어야 한다.

### `01-scope.md` 반영 상태
**이 ADR 시점에는 설계만 완료됐고, `01-scope.md`에는 아직 반영되지 않았다.** 제품 오너가 이 설계를 승인하면 requirements-analyst(오케스트레이터 겸임)가 `01-scope.md` §1.2에 "회원가입"과 "라이센스 관리"를 핵심 스코프 항목으로 추가하고, architect가 `03-data-model.md`(§3.25 `licenses` 신규 절), `04-api.md`(§4.2 인증 절에 `/api/auth/signup` 추가 + 신규 §4.x 라이센스 관리 절), `05-frontend.md`(`/signup`, `/admin/licenses` 라우트 추가)를 뒤이어 갱신한다. 이 작업들은 이번 ADR 범위에 포함하지 않았다.

### developer에게 위임할 구현 범위 (설계 승인 후)
1. `com.lightalm.auth` 패키지: `SelfSignupController`, `SignupRequest`, `SelfSignupService`
2. `com.lightalm.license` 패키지: `License` 엔티티(+ `LicenseType`/`LicenseStatus` enum), `LicenseRepository`, `LicenseFileParser`, `LicenseSignatureVerifier`, `LicenseCommandService`, `LicenseQueryService`, `LicenseEnforcementService`, `LicenseAdminController`, `PublicLicenseStatusController`, 관련 DTO
3. 마이그레이션 2개(§3.3 제안 내용, 구현 시점 번호 재확인 후 생성)
4. 기존 파일 최소 수정: `SecurityConfig`(permitAll 2곳 추가), `JsonAuthenticationSuccessHandler`(라이센스 게이트 A 훅), `UserService`(게이트 A·B 훅)
5. 프론트: `/signup` 페이지(`GuestOnlyRoute`), `/admin/licenses` 페이지(ADMIN 전용), `TopNavbar`에 "라이센스 관리" 링크 조건부 노출
6. qa-tester에게 넘길 검증 포인트: 서명 위조 파일 업로드 거부, 시트 한도 초과 시 가입/관리자생성 모두 차단, 라이센스 만료 시 비-ADMIN 로그인 차단 + ADMIN 로그인 허용, 라이센스 교체로 시트가 줄어도 기존 로그인은 유지되는지, `systemRole`을 조작한 가입 요청이 여전히 `USER`로 저장되는지

### 실제 구현과 설계의 차이 (2026-10-03 구현 완료 시점 기록)
- **마이그레이션 번호 확정**: `V9__create_license_tables.sql`, `V10__add_license_to_audit_target_type.sql` (설계 시점 "제안"과 동일한 번호로 확정됨 — V8 이후 선점한 다른 기능 없었음)
- **`LICENSE_FILE_INVALID`(400) 에러 코드 신규 추가**: §2.3 표에는 `LICENSE_SIGNATURE_INVALID`/`LICENSE_ALREADY_EXPIRED`/`LICENSE_FILE_TOO_LARGE`만 있었으나, JSON 파싱 자체가 실패하는 경우(비정상 포맷 업로드)를 설계에서 놓쳤다. `LicenseFileParser`가 이 경우 500 대신 `400 LICENSE_FILE_INVALID`를 반환하도록 developer가 추가함 — `04-api.md`에도 반영 필요
- **`GlobalExceptionHandler` 수정**: §4.1 "불가피하게 건드려야 하는 기존 파일" 목록에 없었지만, 신규 도메인 예외(`LicenseInvalidException`/`LicenseSeatLimitExceededException`→403, `LicenseFileRejectedException`→400)를 API 에러 코드로 변환하는 지점이 여기뿐이라 불가피하게 추가 수정됨
- **`UserRepository.countByEnabledTrue()` 신규 추가**: 시트 사용량 계산(게이트 B, `/admin/licenses/current`의 `seatsUsed` 표시)에 필요해 추가됨. 설계 문서에 명시되지 않았던 리포지토리 메서드
- **`LicenseDescriptor`의 `issuedAt`/`expiresAt`을 원본 문자열 그대로 보관**: `Instant`/`LocalDateTime`으로 재직렬화하면 발급자가 서명한 원문과 포맷이 미묘하게 달라질 수 있어(예: trailing `.000Z` 유무) HMAC 서명 검증이 깨질 수 있다. 그래서 canonical 문자열 계산에는 원본 문자열을 그대로 쓰고, 비즈니스 로직용으로 `issuedAtInstant()`/`expiresAtInstant()` 파생 메서드를 별도로 둠
- **치명적 버그 수정(qa-tester 발견, REJECT → 재수정)**: `LicenseCommandService.upload()`에서 기존 ACTIVE 라이센스의 `supersede()`(더티 체킹 UPDATE, flush 시점까지 지연)와 신규 `License`의 `save()`(IDENTITY 생성이라 즉시 INSERT)의 DB 반영 순서가 보장되지 않아, 두 번째 라이센스 업로드부터 매번 `uq_licenses_single_active` 유니크 제약 위반(500)이 발생했다. `existing.supersede()` 직후 `licenseRepository.saveAndFlush(existing)`을 호출해 UPDATE를 먼저 DB에 반영하도록 수정하고, 회귀 테스트(`LicenseCommandServiceTest.upload_flushesSupersededExistingLicense_beforeInsertingNewActiveLicense`)를 추가함
