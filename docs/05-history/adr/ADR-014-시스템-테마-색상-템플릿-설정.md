> Owner: architect | Status: Accepted (구현 완료, 2026-10-05) | Date: 2026-10-05

> **[2026-10-05 구현 완료 각주]** developer가 아래 설계를 거의 그대로 구현했다. 실제 코드와의 차이점만 기록한다:
> - 실제 마이그레이션 파일은 `V16__create_system_theme_settings.sql`이다(Phase 22가 V15를 선점했던 상태 — §3의 "가칭 V14" 제안은 예상대로 밀려났다).
> - 패키지: `com.lightalm.theme.{domain,repository,dto,service,api}` — 설계 §7 그대로.
> - `UpdateThemeSettingsRequest.colorPreset`을 `ThemeColorPreset` enum이 아니라 `String`으로 받는다. 이유: 요청 바디의 enum이 알 수 없는 값이면 Jackson이 바인딩 단계에서 `HttpMessageNotReadableException`을 던지는데, `GlobalExceptionHandler`에 이 예외 전용 핸들러가 없어 전역 catch-all로 떨어져 **400이 아니라 500**이 응답된다. 서비스 레이어에서 직접 `ThemeColorPreset.valueOf(...)`로 파싱해 실패 시 `ValidationException`(400)으로 바꾸기 위해 문자열로 받는 쪽을 선택했다(응답 DTO들은 그대로 enum 타입 사용 — 출력 직렬화는 이 문제가 없다).
> - **설계에 없던 범위의 버그를 구현 중 발견해 수정했다(전역 영향)**: `@PreAuthorize("hasRole('ADMIN')")`가 거부하면 Spring Security 6.3+에서 `AuthorizationDeniedException`(`AccessDeniedException`의 하위 타입)이 컨트롤러 메서드 호출 중 던져지는데, `GlobalExceptionHandler`에 이 예외 전용 핸들러가 없어 catch-all(`handleUnexpected`)로 떨어져 **403이 아니라 500**이 응답되고 있었다. `ThemeAdminController`를 실제 curl로 비-ADMIN 사용자로 호출해 재현했고, 이는 `ThemeAdminController`만의 문제가 아니라 `@PreAuthorize`를 쓰는 기존 모든 ADMIN 전용 컨트롤러(`LicenseAdminController` 등)에도 똑같이 영향을 주는 전역 버그였다. `GlobalExceptionHandler`에 `AccessDeniedException` 전용 핸들러(403/`FORBIDDEN`)를 추가해 해소했다 — 이 수정으로 기존 라이센스 관리 API 등의 권한 거부 응답도 함께 올바른 403으로 바뀐다(회귀 영향 없음, 기존 ADMIN 호출 경로는 그대로 200).
> - `ThemeSettingsResponse`의 필드명은 설계 문서의 "updatedBy"가 아니라 `updatedByFullName`으로 구체화했다(응답에 담을 값이 username이 아니라 fullName이라는 점을 필드명에서 바로 알 수 있도록 — ADR §5.4가 "마지막 변경: {fullName}" 표시를 명시했기 때문).
> - 행이 없는 극단 상황에 대한 방어는 조회(`DEFAULT` 폴백)뿐 아니라 변경(`PUT`)에도 적용했다 — 시드 행이 없으면 `ThemeSettingsCommandService`가 `id=1`로 새 행을 만들어 저장한 뒤 적용한다(설계 문서는 조회 쪽 폴백만 명시했지만, 변경 API도 500 대신 정상 동작하도록 대칭적으로 보강).
> - 테스트: 단위 테스트 12개(`ThemeSettingsQueryServiceTest` 4개, `ThemeSettingsCommandServiceTest` 4개) + 권한 검사 전용 테스트 4개(`ThemeAdminControllerAuthorizationTest`) + `GlobalExceptionHandlerTest` 2개(위 403/500 버그 수정 검증), 총 22개 추가. 이 프로젝트에는 `@PreAuthorize` 권한 검사를 검증하는 기존 선례(MockMvc/보안 통합 테스트)가 전혀 없었다(기존 ADMIN 전용 컨트롤러들도 커버되지 않음) — `@WebMvcTest` 대신 `@EnableMethodSecurity`만 올린 최소 Spring 컨텍스트에서 컨트롤러 빈을 직접 호출해 AOP 프록시의 거부/허용을 검증하는 방식을 새로 썼다(DB/Testcontainers 불필요, `mvn test`에서 그대로 실행됨). 시스템 역할은 `ADMIN`/`USER` 둘뿐이라(GLOSSARY §3), 작업 지시문의 "MEMBER/VIEWER" 거부 검증은 프로젝트 역할이라 이 시스템 전역 API와 무관함을 확인하고 비-ADMIN 대표값으로 `USER`를 썼다.
> - `mvnw test` 136개 전체 통과(기존 120개 + Phase 22 후속 보완 2개 + 이 기능 12개 + 403 버그 수정 테스트 2개). 추가로 로컬 docker-compose Postgres(Testcontainers가 아닌 실제 컨테이너, 이 환경은 Testcontainers ryuk 사이드카가 Docker API 버전 불일치로 기동 실패함 — `mvn verify`의 기존 리스크와 동일 현상)에 `mvnw spring-boot:run`으로 떠서 마이그레이션 적용 + `GET /api/public/theme`(비인증) + `GET/PUT /api/admin/theme-settings`(ADMIN 성공, 잘못된 값 400, 비-ADMIN 403) + CORS 헤더(`http://localhost:5173` 오리진)까지 curl로 end-to-end 수동 검증했다.
> - 프론트엔드는 설계 그대로 구현: `applyStoredTheme.ts`(DEFAULT는 `data-theme-color` 속성 자체를 생략), `ThemeContext.tsx`(`ThemeProvider`/`useTheme`), `index.css`(표면 토큰 5종 + 색상 프리셋 4종 속성 선택자 + 다크모드 1종 추가), `main.tsx`(렌더링 전 동기 호출), `TopNavbar.tsx`(다크모드 토글 + ADMIN 전용 "테마 설정" 링크, 기존 `bg-slate-*`/`text-slate-*` 하드코딩을 신규 표면 토큰으로 교체), `AdminThemePage.tsx`(`/admin/theme`), `router.tsx`. `npx tsc -b`/`npm run build`/`npm run lint` 모두 통과. 브라우저 기반 시각 검증(다크모드 토글 실제 렌더링, 스와치 카드 UI)은 이 세션에 브라우저 자동화 도구가 없어 수행하지 못했다 — qa-tester의 다음 검증 항목으로 넘긴다.
> - §1의 "다크모드 범위를 제품 오너에게 재확인 권장" 항목은 이번 구현에서 별도로 재확인받지 않고 ADR 원문의 범위 제한(TopNavbar + `/admin/theme`만) 그대로 구현했다 — 재확인이 필요하면 오케스트레이터가 후속으로 처리해야 한다.

# ADR-014: 시스템 테마(색상 템플릿) 설정 — ADMIN 지정 브랜드 컬러 프리셋 + 라이트/다크 모드

## 맥락 (Context)

제품 오너로부터 다음 요청이 들어왔다(원문 그대로).

> "디자인 부분을 템플릿화하여 SYSTEM_ADMIN 권한을 가진 사용자가 템플릿을 지정할 수 있게 하려고 한다. LG, 삼성, 현대 등 대기업들이 각자의 브랜드 컬러가 있듯이, 지금의 밋밋한 흰 바탕 대신 빨강/파랑 등의 색상을 템플릿으로 선택할 수 있게 디자인 영역을 추가해달라. 그리고 다크모드/라이트모드도 있으면 좋겠다."

### 용어 정정
요청의 "SYSTEM_ADMIN 권한"은 `docs/00-meta/GLOSSARY.md` §3의 `SystemRole`(`ADMIN`/`USER`) 중 기존 `ADMIN`을 가리키는 것으로 해석한다. `SYSTEM_ADMIN`이라는 별도 역할명은 코드/DB 어디에도 없고, GLOSSARY에 없는 동의어를 새로 만들지 않는다는 원칙(GLOSSARY.md 사용 규칙 1)에 따라 이 ADR과 이후 구현 전체에서 **기존 `ADMIN`**으로 통일한다.

### 저작권/상표 리스크 — 02-competitive-reference.md·ADR-008 원칙 적용
요청 원문에 LG/삼성/현대가 예시로 등장하지만, 이 세 기업명이나 그 기업들의 실제 공식 브랜드 컬러 코드를 그대로 쓰면 상표권/저작권 리스크가 있다. `02-competitive-reference.md` 원칙 3·4("기능명은 고유 용어로만 서술", "특정 제품명·회사명을 문서에 직접 적지 않는다")를 그대로 적용해, **"대기업마다 고유 브랜드 컬러를 쓴다"는 개념만 참고**하고, 실제 구현물은 이 프로젝트 자체의 일반적인 색상 이름(레드/블루/그린/퍼플)과 범용 팔레트 색상값(Tailwind 기본 팔레트 계열의 통용 색조 — 특정 기업의 등록 상표 컬러가 아님)으로 새로 정의한다. 이 ADR 본문과 이후 생성될 모든 코드/DB 값에는 기업명을 쓰지 않는다.

### 현재 상태 (코드 확인 결과)
- `frontend/src/index.css`의 Tailwind v4 `@theme` 블록에 이미 색상 커스텀 프로퍼티 4개가 정의돼 있다: `--color-primary`(#5e6ad2), `--color-primary-hover`(#828fff), `--color-primary-focus`(#5e69d1), `--color-brand-secure`(#7a7fad). 참고 문서는 `docs/02-design/design-tokens/linear-style-tokens.md`(SPEC 문서 체계 밖의 참고용 문서, Linear 앱 스타일 참고).
- "테마를 바꿀 수 있는 토큰 구조"는 색상 4종뿐이고, 명암/배경/텍스트 같은 **표면(surface) 계열 토큰은 전혀 정의돼 있지 않다.** 실제 화면 27개 파일에서 `bg-white`/`bg-slate-50`/`text-slate-900`/`border-slate-200` 등 Tailwind 기본 색상 클래스를 **120곳 이상 직접 하드코딩**하고 있다(그레핑 결과 확인). 즉 다크모드를 "전체 화면에 실제로 보이게" 만들려면 이 ADR의 범위를 훨씬 넘어서는 기존 화면 전체 리트로핏이 필요하다 — 아래 결정에서 이 현실을 반영해 범위를 의도적으로 좁힌다.
- 시스템 역할은 `User.systemRole`이 `ADMIN`/`USER` 둘뿐이고(GLOSSARY §3), 기존 ADMIN 전용 API는 `@PreAuthorize("hasRole('ADMIN')")` 패턴을 쓴다(`LicenseAdminController` 확인).
- ADR-011의 `PublicLicenseStatusController`(`GET /api/public/license-status`, `permitAll`, 민감정보 미노출)와 동일한 패턴이 로그인 화면 사전 테마 적용에 그대로 재사용 가능하다.
- `/admin/users`, `/admin/licenses`는 `AdminRoute`(프론트, `user.systemRole !== 'ADMIN'`이면 `/`로 리다이렉트) + `TopNavbar`의 조건부 링크 노출로 보호된다 — 동일 패턴을 새 관리자 화면에도 쓴다.

### 스코프 확장 여부 판단
`01-scope.md`에는 디자인 테마/색상 템플릿/다크모드에 대한 언급이 §1.2(핵심 스코프)·§1.3(비스코프) 어디에도 없다. ADR-008/ADR-011과 동일하게 **완전히 새로운 기능**이며, 이 ADR은 설계만 확정하고 `01-scope.md` 반영은 제품 오너 승인 후 오케스트레이터가 별도로 수행한다.

## 결정 (Decision)

> 이 ADR은 아직 `01-scope.md`/`03-data-model.md`/`04-api.md`/`05-frontend.md`에 반영되지 않은 신규 기능의 설계를 ADR 본문 안에 자기완결적으로 담는다(ADR-011/012/013과 동일한 방식). 각 문서 반영은 승인 후 별도 작업이다.

### 1. 범위 정의 — 색상 프리셋(조직 설정) vs 라이트/다크 모드(개인 설정), 트레이드오프 판단

두 요청을 하나의 설정으로 묶지 않고 **명확히 분리**한다. 이유는 둘의 성격이 근본적으로 다르기 때문이다.

| 축 | 성격 | 이 ADR의 결정 | 근거 |
|---|---|---|---|
| 브랜드 컬러(색상 프리셋) | **조직의 시각적 아이덴티티.** 같은 회사 소속이면 보는 사람이 누구든 같은 색이어야 "브랜드"로서 의미가 있다 | **시스템 전역 설정, ADMIN만 변경** | 제품 오너 요청의 "대기업 브랜드 컬러" 비유 자체가 조직 단위 개념 |
| 라이트/다크 모드 | **개인의 시각 선호/작업 환경.** 같은 조직 소속이라도 주변 조도·개인 눈 피로도·취향에 따라 다른 모드를 쓰는 것이 자연스럽다(업계 다수 SaaS 제품의 일반적 패턴) | **사용자 개인별 선호, 브라우저(localStorage)에 저장 — 서버 저장 안 함** | 조직 설정으로 강제하면 "관리자가 야간 근무자의 눈 건강까지 강제로 결정"하는 셈이 되어 실사용성이 떨어짐. 서버에 저장하지 않아도 되는 이유는 브라우저 로컬 저장소만으로 충분한 정보이기 때문(기기를 바꾸면 다시 선택하면 됨 — 이 정도 불편은 "Light" 철학상 감내 가능) |

이 분리의 실질적 이점: 라이트/다크 모드는 **DB 테이블도 API도 필요 없다.** 클라이언트에서 `localStorage` + `prefers-color-scheme` 미디어쿼리만으로 완결되므로, 서버 측 구현 범위가 "색상 프리셋 하나"로 좁아진다(과설계 방지).

**다크모드 구현 범위의 추가 제한(현실 인지)**: 위 "현재 상태"에서 확인했듯 기존 27개 화면 파일이 Tailwind 기본 색상 클래스를 하드코딩하고 있어, 다크모드를 전체 화면에 적용하려면 그 파일들을 전부 리트로핏해야 한다. 이는 이 ADR 하나의 범위를 넘는 대규모 작업이다. 따라서 이 ADR은:
- **인프라(토큰 체계 + 토글 UI + 공유 레이아웃 1곳)까지만 범위로 정한다.** 신규 표면(surface) 계열 토큰을 정의하고 `TopNavbar`(모든 화면이 거치는 공유 레이아웃)에 라이트/다크 토글을 추가해 즉시 체감 가능한 최소 범위로 먼저 검증한다.
- **기존 27개 화면 전체의 색상 클래스 리트로핏은 이 ADR의 범위에 포함하지 않는다.** `docs/CLAUDE.md` "기존 코드에 대한 예외"(Phase 0~19 레거시 코드는 신규 규칙을 즉시 따르지 않아도 됨)와 동일한 원칙을 적용해, 전면 리트로핏이 필요해지면 별도 ADR/Phase로 다룬다. 이 ADR 구현 직후에는 "다크모드를 켜도 TopNavbar와 신규 `/admin/theme` 화면만 바뀌고, 나머지 화면은 라이트 모드 색상이 그대로 보이는" 상태가 된다는 점을 명시적인 알려진 제약으로 남긴다.

### 2. 색상 프리셋 정의

기존 4개 토큰(`primary`/`primary-hover`/`primary-focus`/`brand-secure`)을 그대로 유지하는 "세트" 단위로 프리셋을 정의한다. **3~5개로 한정**하고, 무한 커스텀 컬러피커는 제공하지 않는다(과설계 방지, 제품 오너 요청에도 없음).

| 프리셋 코드 | 한글 라벨 | `--color-primary` | `--color-primary-hover` | `--color-primary-focus` | `--color-brand-secure` | 비고 |
|---|---|---|---|---|---|---|
| `DEFAULT` | 기본(라벤더) | `#5e6ad2` | `#828fff` | `#5e69d1` | `#7a7fad` | **기존 `index.css` 값과 100% 동일.** 이 프리셋이 선택된 상태는 현재 운영 중인 화면과 시각적으로 완전히 동일해야 하위 호환성이 보장됨 |
| `RED` | 레드 | `#dc2626` | `#ef4444` | `#b91c1c` | `#a85c5c` | 범용 팔레트 적색 계열(Tailwind `red-600/500/700` 수준의 통용 색조) |
| `BLUE` | 블루 | `#2563eb` | `#3b82f6` | `#1d4ed8` | `#5c76a8` | 범용 팔레트 청색 계열 |
| `GREEN` | 그린 | `#16a34a` | `#22c55e` | `#15803d` | `#5c9170` | 범용 팔레트 녹색 계열 |
| `PURPLE` | 퍼플 | `#7c3aed` | `#a78bfa` | `#6d28d9` | `#8a7aa8` | 범용 팔레트 보라 계열 |

어떤 색상값도 실제 특정 기업의 등록 브랜드 컬러 코드를 조사해 그대로 베낀 것이 아니라, 통용되는 웹 디자인 팔레트 색조에서 이 프로젝트가 자체적으로 고른 값이다. 프리셋 이름도 색상 자체를 가리키는 일반 명사(레드/블루/그린/퍼플)이며 기업명을 붙이지 않는다.

### 3. 데이터 모델

**신규 테이블 1개만 추가한다.** 범용 key-value 설정 테이블은 만들지 않는다(과설계 방지 — 지금 필요한 설정 항목은 "색상 프리셋" 하나뿐이므로 명시적 컬럼으로 둔다). 라이트/다크 모드는 §1 결정에 따라 서버에 저장하지 않으므로 컬럼도 만들지 않는다.

#### `system_theme_settings` (신규, 단일 행 테이블)

| 컬럼 | 타입 | 제약 |
|---|---|---|
| id | BIGINT | PK, `DEFAULT 1`, `CHECK (id = 1)` — PK 유니크 + 이 체크로 **행이 항상 정확히 0개 또는 1개**임을 DB 레벨에서 강제(license의 "ACTIVE 1건" 부분 유니크 인덱스 패턴과 달리, 이 테이블은 처음부터 단일 행 전용이라 더 단순한 고정 PK 패턴을 씀) |
| color_preset | VARCHAR(20) | NOT NULL, `DEFAULT 'DEFAULT'`, CHECK IN (`'DEFAULT'`,`'RED'`,`'BLUE'`,`'GREEN'`,`'PURPLE'`) |
| updated_by | BIGINT | FK → `users.id`, `ON DELETE SET NULL` |
| updated_at | TIMESTAMP | NOT NULL, `DEFAULT now()` |

마이그레이션이 적용되는 즉시 `id=1, color_preset='DEFAULT'` 행을 1건 시드해, 이 기능이 배포된 직후에도 **공개 조회 API가 항상 유효한 응답을 반환**하고 기존 운영 화면의 색이 바뀌지 않도록 한다(하위 호환성).

#### 마이그레이션 제안 (참고용 SQL — 실제 파일은 developer가 구현 시점에 생성, 번호는 재확인)
현재 확인된 가장 높은 마이그레이션 번호는 `V13__create_custom_field_tables.sql`이다(2026-10-05 확인). 이 ADR은 **가칭 V14**로 제안하지만, ADR-012의 Phase 21~23(폼레이아웃/열거형/워크플로우) 구현이 이 기능보다 먼저 V14/V15를 선점했다면 developer가 다음 번호로 밀어서 배정한다 — 이 ADR은 번호 자체를 확정하지 않는다(ADR-011 §3.3과 동일한 태도).

```sql
-- (제안) V14__create_system_theme_settings.sql
CREATE TABLE IF NOT EXISTS system_theme_settings (
    id BIGINT PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    color_preset VARCHAR(20) NOT NULL DEFAULT 'DEFAULT'
        CHECK (color_preset IN ('DEFAULT','RED','BLUE','GREEN','PURPLE')),
    updated_by BIGINT REFERENCES users(id) ON DELETE SET NULL,
    updated_at TIMESTAMP NOT NULL DEFAULT now()
);

INSERT INTO system_theme_settings (id, color_preset)
VALUES (1, 'DEFAULT')
ON CONFLICT (id) DO NOTHING;
```

`CREATE TABLE IF NOT EXISTS` + `INSERT ... ON CONFLICT DO NOTHING` 조합으로 재실행해도 오류가 나지 않는 idempotent 형태를 유지한다(ADR-002/006 원칙).

### 4. API

| Method | Path | 설명 | 권한 |
|---|---|---|---|
| GET | `/api/public/theme` | `{ colorPreset: "RED" }` — 색상 프리셋만 반환(민감 정보 없음, 로그인 화면 포함 앱 부트스트랩이 비인증 상태로 호출) | 공개 |
| GET | `/api/admin/theme-settings` | 현재 설정 상세(`colorPreset`, `updatedBy`, `updatedAt`) + 선택 가능한 프리셋 전체 목록(코드+라벨+대표 색상 — 관리자 화면의 스와치 미리보기용) | ADMIN |
| PUT | `/api/admin/theme-settings` | 본문 `{ "colorPreset": "BLUE" }` — 프리셋 변경. 허용되지 않은 값이면 `400 VALIDATION_ERROR` | ADMIN |

라이트/다크 모드는 §1 결정에 따라 **서버 API가 없다** — 클라이언트 전용(§5 참고). 변경 이력 조회 API(히스토리 목록)는 만들지 않는다(라이센스처럼 여러 건을 쌓는 개념이 아니라 단일 설정의 현재값만 의미가 있으므로 — 과설계 방지). `updated_by`/`updated_at`은 "누가 마지막으로 바꿨는지"를 보여주는 최소한의 추적 정보로만 쓰고, `audit_logs` 연동은 하지 않는다(설정 변경 1건이 운영상 중요한 보안/변경 이력까지는 아니라고 판단 — 필요해지면 별도 ADR로 `AuditTargetType`에 추가).

`SecurityConfig`의 `permitAll()` 목록에 `/api/public/theme`을 추가해야 한다(기존 `/api/auth/login`, `/api/auth/signup`, `/api/public/license-status`, `/api/webhooks/**`와 동일한 예외 경로).

### 5. 프론트엔드 적용 방식

#### 5.1 `index.css` 토큰 확장 (전면 재작성 아님 — 기존 4개 토큰 유지하고 속성 선택자로 재정의 레이어만 추가)

```css
@theme {
  /* 기존 4개 — DEFAULT 프리셋 값, 변경 없음(하위 호환) */
  --color-primary: #5e6ad2;
  --color-primary-hover: #828fff;
  --color-primary-focus: #5e69d1;
  --color-brand-secure: #7a7fad;

  /* 신규 — 표면 계열 토큰(라이트 모드 기본값). §1에서 범위를 TopNavbar 등 공유 레이아웃으로 한정했으므로
     이 토큰들을 쓰는 곳도 우선 그 범위로 한정된다 */
  --color-surface: #ffffff;
  --color-surface-muted: #f8fafc;
  --color-text: #0f172a;
  --color-text-muted: #475569;
  --color-border: #e2e8f0;
}

:root[data-theme-color="red"] {
  --color-primary: #dc2626;
  --color-primary-hover: #ef4444;
  --color-primary-focus: #b91c1c;
  --color-brand-secure: #a85c5c;
}
/* data-theme-color="blue" / "green" / "purple" 동일 패턴 — DEFAULT는 속성 자체를 생략(기본값 사용) */

:root[data-color-mode="dark"] {
  --color-surface: #111827;
  --color-surface-muted: #1f2937;
  --color-text: #f1f5f9;
  --color-text-muted: #94a3b8;
  --color-border: #334155;
}
```

`<html>` 엘리먼트에 `data-theme-color`(색상 프리셋)와 `data-color-mode`(라이트/다크) 두 속성을 독립적으로 설정한다 — 서로 다른 축이므로 속성도 분리한다. CSS 커스텀 프로퍼티는 속성 선택자의 명시도가 `:root` 단독보다 높으므로 자연스럽게 재정의된다(일반적인 CSS 테마 전환 기법).

#### 5.2 앱 부트스트랩 흐름 — 깜빡임(FOUC) 방지

1. `main.tsx`에서 `createRoot(...).render(...)` 호출 **이전에**, 새 모듈 `frontend/src/theme/applyStoredTheme.ts`를 동기 호출한다. 이 모듈은 `localStorage`에 캐시된 `lightalm:colorPreset`(없으면 `DEFAULT`)과 `lightalm:colorMode`(없으면 `window.matchMedia('(prefers-color-scheme: dark)')` 결과)를 읽어 즉시 `document.documentElement.dataset.themeColor`/`dataset.colorMode`에 반영한다. 네트워크 요청 없이 동기 실행되므로 첫 페인트부터 올바른 색이 보인다(색이 잘못 보였다가 바뀌는 깜빡임 방지).
2. 신규 `ThemeProvider`(React context, `AuthProvider`와 같은 레벨에서 감쌈)가 마운트 시 `GET /api/public/theme`을 react-query로 호출해, 응답이 로컬 캐시와 다르면(다른 기기/세션에서 ADMIN이 변경한 경우) `data-theme-color`와 `localStorage` 캐시를 갱신한다. 이 호출은 비인증 상태에서도 항상 성공하므로 `/login`, `/signup` 화면에도 동일하게 적용된다(두 화면 모두 앱 루트 안에 있으므로 별도 처리 불필요).
3. 라이트/다크 토글은 네트워크 호출이 전혀 없다 — 사용자가 토글을 누르면 즉시 `dataset.colorMode`와 `localStorage`만 갱신한다.

#### 5.3 라이트/다크 토글 UI
`TopNavbar`에 아이콘 버튼 하나를 추가한다(ADMIN 제한 없음 — 모든 사용자가 쓸 수 있는 개인 설정). 클릭 시 `light`↔`dark` 토글.

#### 5.4 관리자 화면 — `/admin/theme`
- 기존 `/admin/users`, `/admin/licenses`와 동일한 보호 패턴: `AdminRoute`로 감싸고, `TopNavbar`의 "라이센스 관리" 링크 옆에 "테마 설정" 링크를 `user?.systemRole === 'ADMIN'`일 때만 노출.
- 화면 구성: 5개 프리셋을 색상 스와치 카드로 나열(현재 선택된 프리셋 강조 표시) → 선택 → "저장" 버튼 → `PUT /api/admin/theme-settings` 호출 → 성공 시 `ThemeProvider` 상태 갱신(새로고침 없이 즉시 반영) + "마지막 변경: {fullName}, {updatedAt}" 표시.

### 6. 기존 디자인 토큰 문서(`linear-style-tokens.md`)와의 관계
이 문서는 SPEC 문서 체계 밖의 참고용 문서이고, 지금 `index.css`의 4개 색상 값과 정확히 일치한다. 이 ADR이 구현되면 이 문서가 서술하는 팔레트는 **"5개 프리셋 중 `DEFAULT`"로 재해석**되어야 한다. 이 ADR은 문서 수정 권한 밖이므로 실제 각주 추가는 하지 않지만, 구현 완료 후 architect가 해당 문서 상단에 "이 문서는 ADR-014 이후 `DEFAULT` 프리셋의 근거 자료로 재해석됨" 각주를 추가하는 작업을 다음 단계로 남긴다(승인 후 별도 작업).

### 7. 코드 구조 — 신규 기능 패키지 배치
완전히 새로운 기능이므로 `docs/CLAUDE.md`의 기능별 패키지 원칙(`com.lightalm.{기능}/api|domain|repository|service|dto`)을 따른다.

```
com.lightalm.theme/              (신규)
├── domain/   SystemThemeSettings(@Setter 금지, changeColorPreset(preset, updatedBy) 도메인 동사로 상태 변경), ThemeColorPreset(enum: DEFAULT/RED/BLUE/GREEN/PURPLE)
├── repository/ SystemThemeSettingsRepository
├── api/      ThemeAdminController(GET/PUT /api/admin/theme-settings), PublicThemeController(GET /api/public/theme)
├── dto/      ThemeSettingsResponse(관리자용 — colorPreset/updatedBy/updatedAt/availablePresets), PublicThemeResponse(colorPreset만), UpdateThemeSettingsRequest
└── service/  ThemeSettingsCommandService(갱신), ThemeSettingsQueryService(조회 — 공개/관리자 두 응답 분리)
```

`SystemThemeSettingsRepository.findById(1L)`로 항상 단일 행을 조회하고, 행이 없는 극단적 상황(마이그레이션 시드 실패 등)에 대비해 `ThemeSettingsQueryService`가 조회 실패 시 `DEFAULT`로 폴백하는 방어 코드를 둔다(공개 API가 500을 반환해 로그인 화면 자체가 깨지는 상황을 막기 위함).

#### 7.1 불가피하게 건드려야 하는 기존 파일
| 파일 | 변경 내용 |
|---|---|
| `com.lightalm.config.SecurityConfig` | `permitAll()` 목록에 `/api/public/theme` 추가 |
| `frontend/src/index.css` | §5.1의 신규 토큰·속성 선택자 블록 추가(기존 4개 값은 그대로 유지) |

| `frontend/src/components/TopNavbar.tsx` | 라이트/다크 토글 버튼 추가, ADMIN 전용 "테마 설정" 링크 추가 |

## 결과 (Consequences)

### 장점
- 색상 프리셋과 라이트/다크 모드를 서로 다른 성격(조직 설정 vs 개인 설정)으로 분리해, 다크모드 쪽은 DB 테이블·API가 전혀 필요 없어 구조가 단순해졌다.
- `DEFAULT` 프리셋 값이 기존 `index.css` 값과 완전히 동일해, 이 기능이 배포돼도 ADMIN이 명시적으로 변경하기 전까지는 기존 운영 화면이 **픽셀 단위로 동일**하다 — 하위 호환성이 설계적으로 보장됨.
- 신규 테이블 1개(`system_theme_settings`)만 추가하고 범용 key-value 설정 테이블을 만들지 않아, 향후 다른 세션이 "이 설정이 정확히 어떤 의미인지" 코드만 보고 바로 알 수 있다.
- 기업명·실제 브랜드 컬러를 일절 사용하지 않아 상표/저작권 리스크를 피했다(ADR-008/02-competitive-reference.md 원칙 준수).

### 단점 / 리스크
- **다크모드가 전체 화면에 적용되지 않는다는 점이 사용자에게 혼란을 줄 수 있음**: 이 ADR은 다크모드 범위를 `TopNavbar`와 `/admin/theme` 화면으로 의도적으로 한정했다. 토글을 켜도 대부분의 기존 27개 화면(요구사항/이슈/테스트케이스 목록 등)은 라이트 모드 색상이 그대로 보인다. 이는 과설계를 피하기 위한 의도적 결정이지만, 제품 오너가 "전체 화면 다크모드"를 기대했다면 기대와 어긋날 수 있다 — **구현 착수 전에 이 범위 제한을 제품 오너에게 다시 한번 명확히 확인받을 것을 권장**한다. 전체 화면 리트로핏이 필요하다고 판단되면 별도 ADR + Phase로 다룬다.
- **색상 프리셋도 `TopNavbar`/신규 관리자 화면 이상으로는 즉시 퍼지지 않을 수 있음**: 기존 화면들이 `--color-primary`를 실제로 참조하는 Tailwind 유틸리티 클래스(`bg-primary` 등)를 쓰고 있는지는 이번 조사에서 파일별로 전수 확인하지 않았다. developer가 구현 시점에 각 화면이 실제로 CSS 변수를 참조하는지 점검하고, 참조하지 않는 하드코딕 색상이 있다면 이번 기능의 체감 효과가 제한적일 수 있다는 점을 qa-tester에게 전달해야 한다.
- **라이트/다크 모드가 기기 간 동기화되지 않음**: 서버에 저장하지 않으므로 사용자가 PC와 모바일을 오가면 매번 다시 설정해야 한다. "Light" 철학상 감내 가능한 트레이드오프로 판단했지만, 추후 "계정별 선호 저장"이 필요해지면 별도 ADR(이땐 `users` 테이블에 컬럼 추가가 더 적합 — 신규 테이블 불필요)이 필요하다.
- **단일 행 테이블(`system_theme_settings`)의 동시성**: 두 ADMIN이 동시에 설정을 바꾸면 마지막 쓰기가 이긴다(낙관적 락 없음). 설정 변경 빈도가 매우 낮을 것으로 예상되어 이번 설계에서는 낙관적 락을 생략했다 — 문제가 되면 `@Version` 컬럼 추가로 쉽게 보강 가능.

### `01-scope.md` 반영 상태
**이 ADR 시점에는 설계만 완료됐고, `01-scope.md`에는 아직 반영되지 않았다.** 제품 오너가 승인하면 requirements-analyst(오케스트레이터 겸임)가 `01-scope.md`에 신규 스코프 항목으로 추가하고(버전 라벨은 기존 v4 확장 항목들과 함께 묶을지, 별도 라벨을 둘지는 오케스트레이터가 결정), architect가 `03-data-model.md`(§3.30 예상 — 실제 번호는 반영 시점에 재확인), `04-api.md`(§4.28 예상), `05-frontend.md`(§5.23 예상, `/admin/theme` 화면 + `TopNavbar` 토글)를 뒤이어 갱신한다. `GLOSSARY.md`에도 `SystemThemeSettings`/`ThemeColorPreset` 도메인 개념과 `ThemeSettingsSettingsTab` 등 화면 용어를 추가해야 한다(이번 ADR 범위 밖).

### developer에게 위임할 구현 범위 (설계 승인 후)
1. `com.lightalm.theme` 패키지: `SystemThemeSettings` 엔티티(+ `ThemeColorPreset` enum), `SystemThemeSettingsRepository`, `ThemeSettingsCommandService`, `ThemeSettingsQueryService`, `ThemeAdminController`, `PublicThemeController`, 관련 DTO 3종
